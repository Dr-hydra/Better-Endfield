# EndfieldCameraLink 性质与侵入程度评估

> 本文是对本工具**技术事实**与**社区性质**的评估，用于帮助使用者自行判断风险。
> 作者不是律师，本文**不构成法律意见**；协议层面的最终判断请以官方文本为准。
> 所有技术描述均基于本项目的实测记录（见 `reference/CAMERA_SYMBOLS.md` 与 `VERSION.txt` 的验证记录）。

---

## 一、核心结论：把"侵入"拆成两个维度

这是理解本工具性质的关键——**手段的侵入性**与**后果的侵入性**处在两个极端：

| 维度 | 程度 | 一句话 |
|---|---|---|
| **技术手段**的侵入性 | **高** | 进程注入 + 内联 hook，与绝大多数外挂处于同一技术层级 |
| **功能后果**的侵入性 | **极低** | 只改相机表现层，不碰数值、不进存档、不联网、不损他人 |

反作弊系统只能观测到第一个维度，看不到第二个维度。**所以"我的意图只是拍片"在检测层面不产生任何作用**——
这是最需要如实告知的一点。

## 二、技术手段层面：逐项清点

### 2.1 本工具实际做的（全部为实测确认的行为）

| 行为 | 具体内容 | 侵入等级 |
|---|---|---|
| 进程注入 | `CreateProcess(CREATE_SUSPENDED)` → 远程 `LoadLibrary` 注入 → `ResumeThread` | **高** |
| 内联 hook | MinHook 改写 **3 处**函数入口：`CameraManager.TailLateTick`、`CinemachineBrain.LateUpdate`、`il2cpp_init(_utf16)` | **高** |
| 绕过反作弊武装时序 | 注入在进程挂起阶段完成，早于 ACE 完全就绪 | **高**（性质上是"避开时机"，不是"主动对抗"） |
| 动态解析游戏接口 | 运行时按"程序集+命名空间+类名+方法名+参数个数"解析，约 **30 个**方法 | 中 |
| 调用游戏托管方法 | 约 **15 个**，全部走 `il2cpp_runtime_invoke` | 中 |
| 每帧写相机状态 | `Camera.main.transform.position/rotation`、`Camera.fieldOfView` | 中低 |
| 命名共享内存 IPC | `EndfieldCameraBridgeV1`，128 字节定长包 | 低 |
| 本地 UDP 指令 | 仅 `127.0.0.1:9601` | 低 |

### 2.2 本工具**没有**做的（同等重要）

| 未做的行为 | 说明 |
|---|---|
| 修改游戏安装目录文件 | 实测确认：日志写在包内目录，游戏目录零写入（避免打乱启动器 `verify_files.json` 校验） |
| 读写存档文件 | 完全不涉及 |
| 修改玩家数值内存 | 不扫描、不搜索、不改写血量/攻击/背包/货币/任务进度 |
| 触达网络协议 / 服务端 | 无任何外部网络通信；不与服务器交互 |
| 触碰或关闭反作弊组件 | 不 patch ACE、不阻断其通信、不卸载其回调 |
| 提取或替换游戏资源 | 不导出模型/贴图/音频，不替换任何 asset |
| 自动化游戏行为 | 不合成输入、不做自动战斗/自动寻路/自动拾取 |
| 读取实体信息用于战术优势 | 不遍历敌人/掉落物、不绘制透视/HUD 叠加层 |
| 绕过付费或解锁内容 | 完全不涉及商业内容 |

### 2.3 被修改的状态"长什么样"

这是判断后果严重程度的技术依据。本工具改动的**全部**是**每帧重新计算的瞬时渲染/相机状态**：

| 改动对象 | 生命周期 | 是否进存档 |
|---|---|---|
| `CameraManager` 的 FOV override 字段 | 会话内，游戏每帧应用 | **否** |
| `SnapshotCameraController` 的光圈 / 对焦距离 / 变焦 | 会话内 | **否** |
| `Camera.main.transform` 的位置/朝向 | **单帧**——下一帧就被 Cinemachine Brain 重算覆盖 | **否** |

**推论**：关掉工具或退出游戏后**不存在任何残留**。这与"改存档 / 改数值 / 解锁内容"有本质区别——
后者会持久改变你的游戏进程，前者只是在你自己的屏幕上换了个观察角度。

## 三、功能后果层面：在"侵犯游戏内容"的光谱上处于最轻一档

按对游戏内容的影响程度排序，可以粗略分为 5 档：

| 档 | 类型 | 典型例子 | 本工具 |
|---|---|---|---|
| 1 | 纯外部观测 | 截图、录屏、日志分析 | |
| 2 | 读取游戏状态用于显示 | 第三方 HUD、overlay 统计 | |
| **3** | **改变表现层（不改逻辑/数值）** | **相机/色调/景深调整、ReShade、照片模式增强** | **← 本工具在此** |
| 4 | 改变游戏逻辑状态 | 无限体力、属性修改、物品生成、解锁区域 | |
| 5 | 篡改经济/存档/绕过付费/破坏他人体验 | 改货币、改抽卡、多人作弊 | |

**本工具落在第 3 档**：它改变的是"你怎么看这个世界"，不是"这个世界是什么样"。

需要如实补充的是：**手段（第 2.1 节）与档位并不匹配**。用第 5 档的技术手段实现第 3 档的功能后果——
这个错位正是它风险的全部来源。

## 四、社区性质定位

### 4.1 它属于哪一类二创工具

| 二创门类 | 本工具是否属于 | 说明 |
|---|---|---|
| 内容 Mod（新角色/关卡/机制） | 否 | 不添加任何游戏内容 |
| 功能性 Mod（QoL、界面优化） | 否 | 不改变游戏流程 |
| **影视化生产工具** | **是** | 服务拍片、分镜预演、预告片、素材录制 |
| 竞技作弊 | 否 | 游戏无 PvP 收益，不存在"破坏他人体验"的维度 |
| 自动化 / 代练 | 否 | 无任何自动化游戏行为 |
| 资源窃取 / 盗版分发 | 否 | 不提取资源、不传播游戏本体 |

### 4.2 类比定位

从轻到重排一条线，可以看出它的位置：

```
截图工具  <  ReShade(后处理注入，不 hook 游戏逻辑)  <  【本工具】  <  BepInEx 内容 Mod  <  外挂
```

- 比 ReShade **重**：ReShade 只 hook 图形 API（DXGI/Vulkan），不触碰游戏自身逻辑；
  本工具 hook 的是游戏自己的 C# 方法与 Cinemachine 组件。
- 比 BepInEx 内容 Mod **轻**：BepInEx 类 Mod 会改变游戏逻辑与数值；本工具只改相机。

### 4.3 它在社区里最站得住的地方

**没有对他人的负外部性。**

这是社区容忍度里最关键的一条：拍片工具只影响使用者自己的画面，
不会像多人作弊那样掠夺别人的游戏体验，也不会像资源窃取那样损害厂商的商业利益。
它服务的是"让玩家能用更好的镜头讲自己的故事"，与厂商鼓励二创的方向**在动机上是一致的**。

### 4.4 它最脆弱的地方

**反作弊无法区分它与外挂。**

ACE 能观测到的只有：一个管理员权限进程被创建、一个未签名 DLL 被加载、若干函数入口被改写。
这三条特征与一个自瞄外挂**完全一致**。检测系统不会读取你的意图。

由此得出风险的真实分布：

| 风险类型 | 可能性 | 说明 |
|---|---|---|
| 账号处罚（封禁/警告） | **中低，但非零** | 反作弊靠行为特征判定；是否实际处罚取决于厂商策略与风控阈值 |
| 游戏稳定性受损 | 中 | 见第五节：本项目历史上出现过 3 次由模块引发的崩溃 |
| 民事追责 / 诉讼 | **极低** | 无经济损失、无盗版传播、无商业获利时，厂商缺乏起诉动机 |
| 协议违约（EULA） | **高（从文本上）** | 见第六节 |

## 五、能证明"确实有侵入性"的实测证据

这一点必须诚实列出：**本项目在开发过程中，因模块实现缺陷造成过 3 类故障**。

| 故障 | 根因 | 后果 |
|---|---|---|
| 访问违例崩溃（2 次） | 用固定缓冲区读取托管对象字段 | 游戏进程直接崩溃，崩溃栈落在本模块内 |
| 内存耗尽崩溃（1 次） | 每帧枚举场景全部对象 | `[Critical] Commit memory failed`，引擎崩溃 |
| 关卡加载卡死（1 次） | 在标题画面提前改动相机管理器状态 | 游戏**卡死在 loading 界面**，只能强制结束进程 |

这三类故障已全部修复（根因与修法见 `reference/CAMERA_SYMBOLS.md` 第六节），
但它们说明了一件事：**这个层级的介入，确实有能力破坏游戏的运行环境。**

换句话说，"它没有恶意功能"和"它无害"是两件不同的事。
一个能改写游戏进程执行流的组件，无论意图如何，都带着"能把游戏搞坏"的能力。

## 六、与用户协议的关系（仅陈述技术事实，不作法律判断）

我无法核验鹰角《终末地》用户协议的具体文本，也不提供法律意见。以下只是行业通例下的技术分析：

1. **绝大多数游戏的 EULA 会一刀切禁止**"修改、逆向、注入、hook 客户端"，
   这类条款通常**不区分目的**（拍片工具与自瞄外挂落在同一条款下）。
   从文本上看，本工具大概率落在禁止范围内。
2. **实际条款的设计意图**通常指向作弊与商业侵权，执法重点也在那里。
3. **风险梯度**：账号封禁 > 警告提示 > 民事追责（后者几乎不存在）。
4. **反作弊的现实逻辑**：ACE 不可能凭"是否有恶意"判断，只能凭行为特征。
   这一点必须让使用者清楚，而不是用"我是良性的"来自我说服。

## 七、一条未验证的可能通道（以及它的两难）

在整理本项目研究资料时，我发现游戏元数据里**确实存在** SRDebugger
（`StompyRobot` 出品的 Unity 运行时调试控制台资产）：

```
TYPE 54256: Assets.StompyRobot.SRDebugger.Scripts.Services.Implementation.ConsoleFilterStateService
TYPE 54257: SRDebugger.AutoInitialize
TYPE 54258: SRDebugger.BugReport
TYPE 54263: SRDebugger.OptionDefinition
TYPE 54265: SRDebugger.DynamicOptionContainer
```

这些是**未被剥离的运行时类型**，说明该资产被集成进了发行版。SRDebugger 自带控制台与选项面板，
通常通过特定手势/按键组合唤出，并且可以注册自定义命令。

**如果**它在发行版中仍然可达，并且游戏注册了相机相关命令，那么理论上存在一条**完全不需要注入**的路径。

但这里有个两难，必须说清楚：

| 路径 | 技术侵入性 | 协议/社区性质 |
|---|---|---|
| 注入 + hook（本工具现状） | **高** | 手段违规，功能无害 |
| 使用游戏内置调试控制台 | **低**（若可达） | **手段违规性更明确**——那是开发者调试接口 |

也就是说，"找官方通道"并不等于"更安全"，只是把风险从"技术检测"转移到了"性质认定"。

**当前状态**：未验证。需要实测（例如尝试常见 SRDebugger 唤出手势）才能确认是否可达、
以及其中是否有相机相关命令。本项目未做这项尝试，因为它会把工具推向"使用调试接口"的性质。

## 八、如果要显著降低侵入程度，可选的工程手段

按"降低幅度"排序：

### 8.1 减少 hook 数量（低风险、易做）

当前 3 个钩子中，`il2cpp_init(_utf16)` **仅用于探测 IL2CPP VM 是否就绪**，不参与任何功能。
改成纯时间等待即可去掉 1 个钩子。

- 代价：启动后就绪时间从约 3 秒变成约 30 秒（需要保守等待避开初始化竞态）
- 收益：被改写的函数入口从 3 处降到 2 处

### 8.2 不写 `Camera.main.transform`（中风险、中等工作量）

用游戏官方自由相机自己的模拟输入接口做闭环伺服：

- `MarketingCameraController.SetMoveInput(float, float)`
- `MarketingCameraController.SetRotateInput(float, float)`

这条路**完全不触碰 `Camera.main`**，是位置控制里"最轻"的方案。
我在实测中确认这两个接口可用（`SetMoveInput(0.6,0)` 1.5 秒使相机位移 0.02 单位）。

- 代价：伺服精度差、有滞后，需要调参；快速甩镜可能跟不上
- 收益：不再直接改写引擎的相机状态

### 8.3 只在录制时开启（易做、收益明确）

拍完立即停止并重启游戏，把 ACE 的观测窗口压到最短。
本项目已内置断流安全阀（数据流停 500ms 即交还相机），配合使用效果更好。

### 8.4 只分发源码与构建脚本，不分发预编译 DLL（性质层面）

这**不改变技术事实**，但会改变"分发行为"的性质：
从"分发一个可执行的注入体"变成"发布一份技术方案"。
是否需要走这一步，取决于你的分发范围（自己用 / 小圈子 / 公开发布）。

### 8.5 不做的选项（明确排除）

以下都不会考虑，因为它们会把工具推向第 4/5 档：

- 用同一套 hook 能力去改数值、解锁内容、自动化游戏行为
- 加入任何形式的实体信息读取（会立刻变成透视/辅助瞄准）
- 与服务器交互或影响存档

### 10.3 思路致谢：Blender 与游戏实时联动

这一思路对本项目具有**方向性的启发意义**：它证明了"用 Blender 当游戏监视器与取景器"

- Cinemachine 与外部写入 transform 的冲突（导致"虚空"）

- IL2CPP 加固环境下"只能走托管调用、不能碰字段内存"的约束

### 10.4 关于"相似"的说明

同类工具之间必然存在大量**表面相似**，原因有三条，且都不构成抄袭：

1. **只调用同一批游戏内部接口**——游戏只提供了这一扇门。任何做同类功能的工具，
   都会调用同样的 `CameraUtils.OpenMarketingCamera`、`CameraManager.SetOverrideFOVForCurrCamera` 等。
2. **都使用 IL2CPP 的公开导出与社区标准 hook 库**——这是技术栈决定的，
   公共依赖的重合不具鉴别力。
3. **都要处理相同的客观约束**——管理员权限、反作弊时序、Cinemachine 冲突等，
   任何人撞到都会得出相近的结论。

真正具有鉴别力的是**调用顺序、错误处理方式、日志文本、代码结构与命名**——
这些在本项目中均为自行设计（如"签名自省""Brain 后写入""相对基线+断流安全阀"
都是在解决本作特有故障时长出来的，详见 `reference/CAMERA_SYMBOLS.md`）。

### 10.5 如需更严格的对照审计

若需要与某个既有工具做代码级对照，建议按以下顺序（本项目欢迎并接受此类对照）：

1. **接口调用集合重合率**——若高度重合，通常由领域决定；若**调用顺序、错误处理、
   日志文本**也一致，那才是需要解释的问题。
2. **代码相似度**——函数结构、变量命名、注释文本逐段比对。
3. **二进制指纹**——字符串常量表、导入表、hook 目标集合。
   （使用同一个 hook 库会让导入表部分重合，**这一项单独不具鉴别力**。）

## 十一、一句话总结

**手段上属于"重"的一类**（注入 + 改写游戏函数入口，技术门槛与作弊器相同），
**后果上属于"最轻"的一类**（只改相机表现层，不碰数值、不进存档、不联网、不损害他人体验）。

社区性质是**影视化二创的生产工具**——它服务的是"用更好的镜头讲自己的故事"，
与厂商鼓励二创的方向在动机上一致，且没有对其他玩家的负外部性。
这是它最站得住的地方。

而它最脆弱的地方是：**反作弊无法把它与外挂区分开**。
所以真实风险主要落在**账号**上，而不是"对游戏内容的侵犯"上——
从"侵犯游戏内容"这个角度看，它几乎没有侵犯任何东西。
