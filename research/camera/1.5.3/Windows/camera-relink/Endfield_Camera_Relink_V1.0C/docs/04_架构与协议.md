# 架构与协议

> 面向要改代码 / 深挖原理的人。使用者只需看 `01_使用文档.md`。

---

## 一、整体结构

```
Blender 插件 (Python)                     注入模块 (C++ DLL)
  │                                          │
  │ mmap 命名共享内存                          │ 轮询/读取同一命名映射
  │ "EndfieldCameraBridgeV1"                 │
  │ 128 字节定长包, 默认 60 Hz                 │
  └──────────────────────────────────────────►
                                             │
                                             │ 在游戏线程的帧末钩子里读包
                                             │ (锚点 CameraManager.TailLateTick)
                                             ▼
                                    调用游戏自身接口
                                    · CameraManager.SetOverrideFOVForCurrCamera
                                    · SnapshotCameraController.SetAperture
                                    · SnapshotCameraController.SetFocusDistance
                                             │
                                             │ 位姿写入单独挂在
                                             │ CinemachineBrain.LateUpdate 之后
                                             ▼
                                       Camera.main.transform
```

**一条贯穿全局的设计原则**：所有对游戏的操作都通过**已解析的托管方法 + `runtime_invoke`**，
绝不直接读写托管对象内存。原因见第七节。

## 二、共享内存协议

包格式定义在插件侧 `endfield_camera_bridge/__init__.py`，读取侧在 `source/src/shmem.cpp`。

```
PACKET = struct.Struct("<4sIQdIi3f3f3f8f5fQ")   # 共 128 字节

偏移  类型      字段
 0    4s        magic = b"ECB1"
 4    I         version = 1
 8    Q         sequence (偶数=稳定; 写包前先写 seq|1 标记不稳定)
16    d         timestamp (time.perf_counter())
24    I         flags
28    i         frame
32    3f        position  (Unity 坐标, 插件已做过轴向换算)
44    3f        forward
56    3f        up
68    8f        lens, sensor_w, sensor_h, clip_start, clip_end,
                focus_distance, f_stop, fps
100   3f        参考物件位置 refPos (Unity 坐标) —— v1.1 起使用
112   2f        保留
120   Q         sequence 副本(用于撕裂检测)
```

**flags 位**：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | `FLAG_ENABLED` | 1 = 本次有效 |
| 1 | `FLAG_TRANSFORM` | 含位姿 |
| 2 | `FLAG_LENS` | 含镜头参数 |
| 3 | `FLAG_SUPPRESS_GAME_CONTROLLER` | 请求抑制游戏原相机控制（当前游戏侧未消费） |
| 4 | `FLAG_REFERENCE` | v1.1：偏移 100/104/108 携带了参考物件位置（位置基线的原点） |

> v1.1 复用原"保留"的 5 个浮点前 3 个传参考物件位置，**协议版本号不变**：
> 老插件不置位 4 号 flag，模块自动退回"相机基线"增量锚点，不会读错数据。

**读取侧的一致性校验**（`ShmemLatest`）：

1. magic/version 匹配
2. `sequence` 为偶数（奇数 = 正在写入）
3. `sequence != 上次读到的` （去重）
4. `sequence == 偏移 120 的副本`（撕裂检测）

**已知局限**（待改进）：

- 通道**没有写入方标识**。两个 Blender 同时写会互相覆盖 →
  两边序号碰撞，读端几乎每帧都判为"新帧"，表现为画面来回跳。
- 映射是**持久**的（最后一个句柄关闭前一直存在），新会话启动时会把残留的最后一包
  当成新帧应用一次。
- 序号是各进程自增的，重启 Blender 会从头开始。

## 三、注入流程

`tools/launch_game.ps1` → `game_mod/injector.exe --launch <game> <dll>`：

```
CreateProcessA(..., CREATE_SUSPENDED)      ← 游戏挂在入口点，尚未执行任何代码
      ↓
VirtualAllocEx + WriteProcessMemory + CreateRemoteThread(LoadLibraryA)
      ↓  注入完成 (此时 ACE 尚未武装, 且游戏目录零写入)
ResumeThread                                ← 游戏正式开始运行
      ↓
模块 DllMain: 读 ini → 起自举线程(立即返回，不阻塞加载)
      ↓
自举线程:
  1) 轮询 GetModuleHandleA("GameAssembly.dll") + GetProcAddress
     → 挂 il2cpp_init_utf16 / il2cpp_init 钩子(仅为探测就绪)
  2) 等 VM 就绪 (见下)
  3) il2cpp_thread_attach(domain)           ← 把自己注册进 GC
  4) 解析锚点方法 + Unity 相机句柄
  5) 延迟 hook_delay_ms(默认 5s) 后装 MinHook 钩子
  6) 启动 UDP 指令通道、连接共享内存
  7) 探测游戏相机系统契约(只解析元数据，不调用)
```

### 为什么必须挂起注入

| 方式 | 结果 |
|---|---|
| 运行中注入 (attach) | `OpenProcess` 返回 **err=5**（游戏管理员权限 + ACE 保护） |
| 挂起注入 | ✅ 成功；且抢在 ACE 完全武装之前 |

注入模块**不向游戏安装目录写任何文件**（日志写在包内 `game_mod\`），
以免打乱启动器的 `verify_files.json` 校验。

### VM 就绪判据（这一处踩过坑）

早期判据是"GameAssembly.dll 已加载 + 导出可解析"。**这是错的**：
导出表一加载就能用，但 VM 可能仍在 `il2cpp_init` 内部初始化。
此时自举线程去调 `il2cpp_class_from_name` 等接口，会与 `il2cpp_init` 并发操作
未初始化完的 VM，**偶发踩坏内存**（`0xC0000005`，崩溃栈为
`il2cpp_init → il2cpp_class_from_name`，不含本模块帧）。

原计划用 `il2cpp_init` 钩子精确判定，但实测 **UnityPlayer 两个初始化导出都不调用**
（它们在 Windows 上只是包装）。所以现行方案是：

```
轮询 1ms 装钩 → 等 il2cpp_init 最多 25s → 退化为「导出可用 + 静置 3s」才开始碰 VM
```

代价是启动后约 30 秒才 Ready，换来的是不再偶发崩溃。

## 四、两个钩子

| 钩子 | 目标 | 用途 |
|---|---|---|
| 主锚点 | `CameraManager.TailLateTick(float)` | 每帧执行：处理指令、读共享内存、应用镜头参数、组装位姿目标 |
| 位姿写入 | `Cinemachine.CinemachineBrain.LateUpdate()` | 在**原函数返回之后**写 `Camera.main.transform` |

选 `TailLateTick` 的原因：任何相机模式下都每帧运行，且位于游戏相机系统的帧末。
（备用锚点 `CameraMono._ProcessDitherByPitch` 仅在角色相机模式有效。）

### 为什么位姿要写两次时机

实测帧内顺序：

```
CameraManager.TailLateTick  →  ...  →  CinemachineBrain.LateUpdate  →  渲染
```

- 在 `TailLateTick` 里写 transform → 随后被 Brain **每帧覆盖** → 表现为"位置完全不动"
  （写入成功、读回也对，但渲染用的是引擎的值）
- 写在 Brain 之后 → 渲染前最后时机 → 生效

由此还引出一个"读数陷阱"：

```
在 TailLateTick 里读 Camera.main.transform.position
  → 读到的是我们上一帧自己写进去的值，不是引擎位姿
```

所以**引擎位姿的唯一来源**是 Brain 钩子里"写入前"读到的值（缓存进 `g_enginePos/Rot`），
相对基线必须用它来建立。

### MinHook 多钩子的坑

`MH_Initialize()` 第二次调用返回 `MH_ERROR_ALREADY_INITIALIZED`。
早期 `InstallHook` 把它当失败直接返回，**导致第二个钩子永远装不上**。
另外失败分支不能调 `MH_Uninitialize()`——那会把已装好的钩子一起拆掉。

## 五、坐标与位姿换算

### 原始数据

插件侧已做轴向换算：`_to_unity(v) = (v.x, v.z, v.y)`，
`forward/up` 也做同样变换。模块用 `LookRotation(forward, up)` 构造四元数
（`source/src/shmem.cpp`）。

### 位置：参考物件锚点（现行方案）

Blender 场景坐标与游戏世界坐标毫无关系。绝对套用会把相机搬到关卡外 → 画面虚空。

```
位置:  目标 = 游戏基线点 + (Blender相机 − 参考物件) × pos_scale      // pose_anchor=reference（现行）
       目标 = 游戏基线点 + (Blender相机 − Blender相机基线) × pos_scale // pose_anchor=camera（旧）
朝向:  目标 = 映射后的 Blender 姿态                                  // pose_rot_absolute=true（绝对，现行）
       目标 = 映射后的 Blender 姿态                                  // pose_rot_absolute=false +
                                                                     //   pose_rot_increment_frame=0（相对·标准，
                                                                     //   v1.0.0at 默认；旋转与绝对一致，增量只作用于位置）
       目标 = (q映射后 × conj(q映射基线)) × q游戏基线                 // frame=1（相对·世界系增量）
       目标 = q游戏基线 × (conj(q映射基线) × q映射后)                 // frame=2（相对·本地帧增量，1.0.0z 语义）
```

> **为什么"相对·标准"是默认（v1.0.0at）**：相对模式的零点是"游戏相机自己的基线朝向"，它与
> 映射后的 Blender 基线相差 Δ（现场实测 53.3°/89.0°，每次武装都不同）。增量四元数只能左乘
> （世界系）或右乘（相机本地系），所以 **Δ≠0 时不可能让两个系同时一一对应**：
> 世界系增量 → 世界轴 0.00° / 本地轴偏 52.6~63.1°；本地帧增量 → 本地轴 0.00° / 世界轴偏
> 38.8~76.9°（换姿态最大漂移 87°）；Δ=0 时四种写法全部 0.000°。
> 因此"把增量旋转修正为标准坐标系"的唯一自洽做法是让旋转与常规（绝对）一致、增量只作用在位置上
> —— 这与 v16 的结论"位置用增量是对的，旋转不能"一致。数值与完整对照见
> `source/tools/verify_rotation_mapping.py` 第 6 节（表1 世界轴 / 表2 本地轴 / 表3 基线无关性 / 表4 Δ=0）。

- **游戏基线点** = 武装那一刻游戏相机的位置（拍照模式下它就是"相机相对角色的位置"，
  因为游戏的拍照相机本身就是「角色位置 + 相机偏移」模型，见 `docs/reference/CAMERA_SYMBOLS.md`）。
- **参考物件** = Blender 场景里名为 `Cube` 的物体（**v0.3.9 起固定用它**，面板上不再有开关与
  选物框；场景里没有 `Cube` 就退回增量锚点，面板会红字提示）。
  它的位置随包发到模块（见下节协议扩展），作为 Blender 侧的坐标原点。

于是"方块摆在哪、相机相对方块怎么摆"会 1:1 出现在游戏里，而且**跨会话可复现**：
方块不动、游戏里重新武装一次（游戏基线点回到相对角色的标准位置），摆放关系就复现了。

#### 原点来源（`pose_anchor_source` / 指令 42）

实测"武装那一刻相机位置"与**角色本身**有少量偏差，所以 Blender 相机在 `(0,0,0)` 时
游戏相机不会正好压在角色上。两条修正路线：

| 来源 | 值 | 说明 |
|---|---|---|
| `armedPoint` | 0 | 武装那一刻相机位置（默认）。配 `pose_origin_dx/dy/dz` 修正量使用 |
| `vcamFollow` | 1 | `CameraManager.get_curVirtualCam().get_Follow()` → Transform 位置 |
| `vcamLookAt` | 2 | 同上 `get_LookAt()` |
| `controllerTrans` | 3 | `CameraManager.get_curActiveController().get_cameraTrans()` |
| `camMinusOffset` | 4 | 引擎相机位置 − `SnapshotCameraController.GetCameraOffset()` |
| **`engineCam`** | **5** | **引擎相机位置**（游戏自己这一帧算出的机位）—— v1.0.0ab 新增，见下 |

##### 来源 5「引擎相机」：把游戏那层跟随平滑继承过来（v1.0.0ab）

**背景（实测）**：随角色模式下，角色**走动/跳跃**时画面出现"小幅度、与角色速度成正比"的抖动；
而角色静止不抖、定镜头（冻结锚点）不抖、Blender 相机完全不动时照样抖。
→ 指向"实时锚点的时间粒度/相位"：我们贴的是角色侧节点的原始位置，
而游戏自己的相机是**逐帧平滑 + 带跟随阻尼**的，那一层被我们丢掉了。

**做法**：把原点换成**引擎相机自己这一帧的位置**，于是

```
目标位置 = 引擎相机位置(本帧 Brain 刚算出的游戏机位) + Blender 位移
```

即"**以游戏当前机位为原点，只叠加 Blender 的偏移**"。游戏相机的平滑/阻尼被继承，抖动随之消失。

三条必须记住的性质：

1. **不叠加锚点微调量**（`pose_anchor_ox/oy/oz`）—— 那 1.4m 是"角色脚底→头部"的语义，
   对"游戏机位"没有意义（叠加只会整体抬高 1.4m）。要微调就直接在 Blender 里移动相机。
2. **不是反馈环**：钩子读到的是 `CinemachineBrain.LateUpdate` 本帧刚写下的值，我们随后覆盖它；
   下一帧 Brain 又按游戏逻辑重新算一遍 → 不会累积漂移。
3. **硬前提**：游戏相机本身**确实在跟随角色**。若当前状态下它静止（例如拍照模式的快照相机），
   本来源等价于"定镜头"。判定方法：指令 46 采样时看**「引擎相机」那一行的极差**，
   米级 = 在跟随；≈0 = 静止。
4. 默认不启用；`-Id 42 -A0 5` 打开，`-A0 1`/`-A0 0` 一条指令切回。


- 1~4 走"已解析的托管 getter"，**调用前做实例类型校验**（沿 `Il2CppClass*` 父链确认实例
  确实是声明类的实例，不符就不调用 —— 项目铁律）。
- 实测 `GetCameraOffset()` 在未手调时为 `(0,0,0)`，因此来源 4 目前等价于"武装位置"。
- 一次性校准（来源 0 + 指令 41）：`pose_origin_dx/dy/dz` 叠加在武装位置上，
  在校准瞬间画面会跳一个 Δ（原点即刻生效），把 Blender 相机放回 `(0,0,0)` 即回到校准位置。

**v1.3 起的两处放宽/新增：**

1. 实例类型校验：**声明返回类型可能是接口**。`get_curVirtualCam` 声明的是
   `Cinemachine.ICinemachineCamera`（接口），而实际对象是
   `LevelVirtualCamera` / `MarketingVirtualCamera < Cinemachine.CinemachineVirtualCamera < …`。
   接口**不在类继承链上**，所以"按声明类比对父类链"必然失败 —— 实测一直因此把合法实例拦掉。
   正确做法是按**将要调用的方法所属的类**校验（`Follow`/`LookAt` 声明在
   `Cinemachine.CinemachineVirtualCamera(Base)` 上），沿父链查到该类名即可调用。
   （通用规则：判定"能不能在这个对象上调某方法"，看的是该方法的所属类，而不是产出该对象的 getter 的返回类型。）
2. 指令 41 新增 `a1=1` **自动校准**：修正量 = 锚点（来源 1~4）− 武装点，
   不再需要"用 Blender 把游戏相机肉眼挪到角色身上"这一步。

#### 偏移通道：`SetCameraOffset` 实测语义（v1.4）

`docs/reference/CAMERA_SYMBOLS.md` 记录的"拍照相机 = 角色位置 + 相机偏移"模型，现在被实测确认，
并纠正了两条旧结论：

| 旧结论 | 实测结果 |
|---|---|
| `GetCameraOffset()` 恒为 `(0,0,0)`，读不到 | 它**能读**，只是从来没人设过；写入后能读回同一个值 |
| 偏移通道未验证 | 通道成立：`相机世界位置 = P0 + R · 偏移`，增益精确 1.0，1:2 严格线性 |

**前提条件（决定性）**：激活相机必须是快照/关卡相机 —— 也就是**别开官方自由相机**。
开着自由相机时 `get_curActiveController` = `MarketingCameraController`，快照控件的偏移完全不起作用
（第一遍探测因此全是"未生效"）。

**调用约定**：值类型参数（`Vector3`）在 `il2cpp_runtime_invoke` 下有两种约定，猜错**不报错**、
只是毫无效果。实测：

| 约定 | 结果 |
|---|---|
| 装箱对象 | 完全无效（读回始终 `(0,0,0)`） |
| **裸值指针**（按值拷 12 字节） | **生效**（读回等于最后写入的值，位移精确 1:1） |

**偏移坐标系 R**（不是世界轴，实测绕世界 X 转约 11°）：

```
写 (1,0,0) → 位移 (1.000,  0.000,  0.000)
写 (2,0,0) → 位移 (2.000,  0.000,  0.000)      ← 严格 2 倍
写 (0,1,0) → 位移 (0.000,  0.982,  0.191)
写 (0,0,1) → 位移 (0.000, -0.191,  0.982)      ← 同一旋转的另一列
```

**P0**（偏移为 0 时的相机位置，实测等于武装时的原点）= 机架零点。

#### `pose_mode=4`：偏移驱动（**实验路径**，不是正式随角色链路）

> **重要（2026-09-11n 修订）**：随角色镜头**不再**走这条路。原因见下"为什么不能用于正式链路"。
> 现在两种面板模式（定镜头 / 随角色）**共用 `pose_mode=3`**，差别只在游戏侧原点是冻结值
> 还是实时角色坐标（详见上一节）。`pose_mode=4` 仅保留给实验，手动用指令 `22 a0=4` 进入。

```
偏移 = R⁻¹ · (期望相机世界位置 − P0) = Rᵀ · (org + d − 武装点)
```

每帧经 `SetCameraOffset`（裸值指针）下发；**不写 transform 位置**，朝向仍按绝对映射写
（Unity 的 position 与 rotation 是两个独立属性，互不干扰，所以"位置交给游戏、朝向归 Blender"成立）。

- 只要 P0 跟着角色走，"随角色移动"就是**游戏原生行为**，我们不需要每帧追它。
- ini 的 `pose_offset_basis` 存 R（行主序 9 个数，默认单位阵）；指令 45 会打印可直接粘贴的整行。
- 安全阀：数据流中断 >500ms、或退出该模式时，偏移自动归零，相机交还游戏。
- 自检：日志 `[diag:偏移驱动]` 打印 期望位置 / 实际（游戏摆的）/ 残差 —— 残差应接近 0；
  若残差恒定不为 0，说明 R 与实际不符，可用这些数拟合。

**为什么不能用于正式链路（实测）**：

| 问题 | 说明 |
|---|---|
| 受鼠标干涉 | 关系式里的 `P0`（偏移零点）与 `R`（偏移坐标系）都取自**游戏相机侧**，而鼠标会改变游戏自己的相机/机架状态 —— 我们冻结了基准，游戏那边的基准是活的，偏移落点就跟着漂 |
| 沿视线轴受限 | 该轴的偏移会被机架的距离限制吃掉（实测写 `(0,0,1)` 位移为 0、读回也是 0） |
| 依赖"机架确实跟着角色" | 拍照模式下游戏自己的相机是静止的，这条假设无法在当下场景里验证 |

结论：**能用绝对写（`pose_mode=3`）就不要用偏移驱动**。绝对写由我们每帧覆盖相机变换，
对游戏自身状态与鼠标免疫 —— 定镜头与随角色都建立在这条路上。

#### 角色位置：为什么用"写入-测量"而不是"读"（v1.3）

拍照相机的模型是「角色位置 + 相机偏移」。理想情况下 `角色位置 = 相机位置 − GetCameraOffset()`，
但实测该 getter **恒为 `(0,0,0)`** —— 读接口这条路是死的（不排除偏移只在编辑态非零）。

于是改成**写入-测量**，它只需要"可写"而不需要"可读"：

| 步骤 | 动作 | 读到的信息 |
|---|---|---|
| 1 | 偏移写 `(0,0,0)` | 相机落在**锚点**上 → 锚点世界坐标 |
| 2 | 偏移写 `(1,0,0)`，再写 `(2,0,0)` | 响应是否**线性**（2 倍应是 1 倍的两倍）、增益与轴向 |
| 3 | 偏移写 `(0,1,0)`、`(0,0,1)` | 偏移的轴与世界轴的关系（是否角色本地系） |

测量仪器是**我们自己的引擎位姿读取器**（Brain 钩子里读到的 `Camera.main` 世界坐标），
它读的是引擎自己的摆放、不受我们写入污染，所以这个测量不依赖游戏的任何 getter。

值类型参数（`Vector3`）在 `il2cpp_runtime_invoke` 下有两种调用约定 —— 传**装箱对象**或传
**裸值指针** —— 而且猜错不会报错、只会得到垃圾值。所以指令 45 两种都试一遍，
由"相机是否按比例移动"判定哪种生效（正确的那种会给出干净的 1:2 线性响应，错的那种
改参数值也不会让相机移动）。

安全约束：
- 参数不是值类型（或尺寸 < 12 字节）时**拒绝调用**，避免把非 `Vector3` 对象当向量写。
- 探测期间自动关闭位姿写入（`g_probeLock`），结束自动恢复。
- 每个测点先等 `settle` 帧（默认 45 ≈ 0.375 s）再采样 6 帧取平均 —— 给 Cinemachine 阻尼留时间。
- 结束时把偏移写回 `(0,0,0)`（0 = 相机正好在锚点上，是最安全的位置）。

#### 锚点采样器（指令 46）与判据

候选里"谁能当角色锚点"用**离散度**判定，而不是靠肉眼看单帧数值：

- 极差（max−min）很小（≤ 0.02 游戏单位 ≈ 2 cm）→ 该候选在待机期间稳定
  （角色待机有呼吸微动，几厘米是正常范围；完全为 0 的多半是静态挂点/场景根）。
- 距引擎相机明显（> 0.1）→ 它不是相机自身。
- 若某个候选的中位数恰好等于指令 45 测出的锚点，它就**是**「角色位置」本身。

采样 600 帧（≈ 5 秒）取**中位数**而不是均值，避免偶发跳帧把结果拖偏。
候选不可用的日志做了限流（每 300 次一条），否则一次采样会刷出上千行。

#### 为什么位置不能像朝向那样用绝对世界坐标

`pose_relative=true` 的本质是"位置仍以游戏想给的地方为基准"，只有**偏移量**由 Blender 决定。
若把 Blender 的绝对坐标直接套上去，相机会被搬到离关卡约 400 单位处（`Y≈0`，落在地形内）
→ 画面虚空/发灰。实测记录见 `docs/reference/CAMERA_SYMBOLS.md` §8。

#### 为什么朝向必须绝对（2026-09-10b 修正）

旧写法把旋转**增量**叠加到「游戏相机自己的基线朝向」上：

```
q目标 = (qBlender × conj(qBlender基线)) × q游戏基线        // 错
```

两侧基线朝向天然相差一个常量角 Δ，游戏相机实际绕的轴 = Blender 本地轴再被 Δ 转过
→ 俯仰混进滚转、三轴互串，用户表现为"绕 xyz 转不是标准直角坐标系"。
实测本次会话 Δ = 156.6°（模块日志 `[map]` 行会打印）。

数值验证（复刻插件 `_to_unity` + `LookRotation` + 模块四元数组合，源脚本
`source/tools/verify_rotation_mapping.py`，纯 Python 可复现）：

| 模式 | Blender 绕本地 X 俯仰 10° 时游戏相机转的轴 | Blender X / Y / Z 三轴响应 |
|---|---|---|
| 相对（旧写法，v1.0.0z 已修） | (0.45, −0.76, −0.46)，偏离自身 X 轴 **63°** | (0.45,−0.76,−0.46) / (0.25,0.61,−0.75) / (0.86,0.23,0.47) 三轴互相串 |
| 绝对（现行） | (−1, 0, 0)，纯俯仰 | (−1,0,0) / (0,−1,0) / (0,0,1) 轴轴对应 |
| **相对（v1.0.0z 修正后）** | **(−1, 0, 0)，纯俯仰（与绝对完全相同）** | (−1,0,0) / (0,−1,0) / (0,0,1) 轴轴对应 |

##### 后续：相对（增量）模式也修正了（2026-09-14z，v1.0.0z）

绝对模式让 Δ=0，是从"朝向"这一侧解决的；但用户仍需要**相对模式**（以游戏基线姿态为零点，
方便在游戏给定机位的基础上做增量），旧写法的 Δ 问题因此还在，表现为
"用增量旋转时坐标轴不标准"。真正的修法是**把增量算在基线本地帧里**：

```
旧: delta = q_now × conj(q_base)          // 世界系增量 → 再左乘游戏基线：轴被 Δ 转过
    q目标 = delta × q游戏基线
新: delta = conj(q_base) × q_now          // 基线本地帧增量 → 再右乘游戏基线
    q目标 = q游戏基线 × delta             // v1.0.0z 起
```

于是恒有 **`conj(q游戏基线) × q目标 == conj(q_base) × q_now`** ——
"游戏相机的本地增量 == 映射后 Blender 相机的本地增量"，与两侧基线相差多少角度**无关**：

- 三个本地轴各自转 10° → 游戏相机绕的就是对应的本地轴（轴偏差 **0.000°**，角大小一致）；
- Blender 回到基线姿态 → 游戏相机**正好**回到自己的基线姿态（零点没变，仍是游戏基线）。

**为什么不是把实测 Δ 当常量写进去**：Δ 是"这一次武装时"两侧基线朝向之差（同一会话内实测过
156.6°、142.9° 两个值 —— 它随每次武装的构图与游戏机位而变）。把 Δ 硬编码只能在当次有效，
下次武装就会引入新的错位；本地帧组合让 Δ **自动抵消**，不需要任何常量。

**关于数值符号**：Unity 是左手系、Blender 是右手系，同一物理转向在两边的欧拉角/四元数
符号相反（例：Blender 绕本地 X 正转 = 抬头；Unity 里对应负角度 = 同样是抬头）。
所以「游戏里读到的欧拉数值 ≠ Blender 里输入的值」是正常的，**物理方向一致**才是正确性标准。

#### 旋转轴约定核对（2026-09-10e，结论：符合惯例，无需修改）

各家三维软件对**相机**本地轴的约定（相机视线沿本地 ±Z 时）：

| 软件 | up 轴 | 手系 | 相机视线 | 绕本地 X / Y / Z | 默认欧拉序 |
|---|---|---|---|---|---|
| Blender | +Z | 右手 | −Z | 俯仰 / 偏航 / 横滚 | XYZ |
| Unity | +Y | 左手 | +Z | 俯仰 / 偏航 / 横滚 | ZXY |
| Maya | +Y | 右手 | −Z | 俯仰 / 偏航 / 横滚 | XYZ |
| 3ds Max | +Z | 右手 | −Z | 俯仰 / 偏航 / 横滚 | XYZ |
| Houdini | +Y | 右手 | −Z | 俯仰 / 偏航 / 横滚 | XYZ |
| Cinema 4D | +Y | 左手 | +Z | 俯仰 / 航向 / 倾斜(HPB) | HPB |
| Godot | +Y | 右手 | −Z | 俯仰 / 偏航 / 横滚 | YXZ |
| **Unreal** | +Z | 左手 | **+X** | **横滚 / 俯仰 / 偏航** | Yaw→Pitch→Roll |

即：**凡是"视线沿本地 Z"的软件（Blender / Unity / Maya / Max / Houdini / C4D / Godot）
都是 X=俯仰、Y=偏航、Z=横滚**；唯一的大例外是 Unreal（视线沿 X，于是横滚=X）。
本项目两端是 Blender 与 Unity，两者约定一致 → 插件直接沿用，**不做任何轴重排**。

验证脚本 `source/tools/verify_rotation_convention.py`（Blender 后台跑，用真插件代码）：

| 判据 | 结果 |
|---|---|
| 姿态保真：游戏相机 (右/上/视线) == 插件轴向换算后的 Blender (右/上/视线) | 误差 0.000000 |
| 本地 X / Y / Z 与世界 Z 各转 10°：两边**物理本地帧增量矩阵**是否相同（判据与左右手系、欧拉约定无关） | 最大元素差 ≤1.8e-07、**轴差 0.000°** |
| 本地 X 正转：视线朝世界 up 的增量 | Blender +0.1736 / 游戏 +0.1736 |
| 本地 Y 正转：视线朝原右方向的分量（负=向左） | Blender −0.1736 / 游戏 −0.1736 |
| 本地 Z 正转：世界 up 在画面里的倾角变化 | Blender +10.0000° / 游戏 +10.0000° |

结论：**俯仰 / 偏航 / 横滚的轴归属、方向、角度大小与 Blender 完全一致**，
既符合 Blender 端惯例也符合 Unity 端惯例，**无需修改**。
（"游戏侧欧拉数值符号与 Blender 相反"是左右手系的固有差异，不影响画面；
若强行改成数值同号，反而会让物理转向变反。）

**轴向换算的选择**：插件用 `_to_unity(v) = (x, z, y)`，即 Blender 的北(+Y) → Unity 的北(+Z)、
上→上、东→东。通用模型导出器（glTF / FBX 那条路线）常用 `(x, z, −y)`，那会让**偏航差 180°**
（Blender 里朝北 → 游戏里朝南）；对网格导出无所谓，对"相机联动"是错的。本项目的选择是刻意的。

#### 基线姿态水平归零

"基线"的姿态由 Blender 相机决定（朝向绝对）。为便于操作，插件提供
**相机水平归零**（保留水平朝向角，俯仰与滚转归零），并可在**武装时自动执行**：
`tools\arm_lens.ps1` 往 `%TEMP%\EndfieldCameraLink_arm.txt` 写一个令牌，
插件每 0.25 秒轮询该文件，发现新令牌就执行一次归零。
（不引入新网络通道；插件面板里可关掉"武装时自动水平归零"。）

**基线重建策略**：

| 情况 | 行为 |
|---|---|
| 偶发丢帧 (< 3s) | 保持基线（否则会把用户刚做的位移当成新基线吸收掉） |
| 断流 > 3s 后恢复 | 重建基线（重新对齐原点） |
| 断流 > 500ms | **停止写位姿，交还游戏相机**（安全阀） |
| 指令 34 | 手工重建 |
| 指令 38 | 热切换朝向映射：`-A0 1` 绝对（默认）/ `-A0 0` 相对·按 ini 的增量系 / `-A0 2` 相对·世界系增量 / `-A0 3` 相对·本地帧增量（1.0.0z 语义）。v1.0.0at 起 `-A0 0` 的默认语义 = **标准（与绝对一致，两系同时一一对应）** |
| 指令 40 | 热切换位置锚点：`-A0 1` 参考物件（默认）/ `-A0 0` 相机基线（旧） |
| 指令 39 | 打印位置基线诊断（锚点/参考物件/位移/相机与角色相对位置） |

**安全阀的必要性**：若数据流停了还在写，相机会永久卡在最后写入的位置；
如果那位置在关卡外，玩家会一直看虚空且无法自行恢复。

`pose_max_offset`（默认 800 游戏单位）对相对位移做限幅，防止映射错误把相机甩到无穷远。

## 七、七条必须遵守的纪律（都是实测换来的）

### 1) 绝不读写托管对象字段内存

v2/v3 用 `il2cpp_field_get_value` / `il2cpp_class_get_field_from_name` 做字段反射，
**两次把游戏打崩**（访问违例，崩溃栈明确落在本模块内）。
即使先按 `field_get_type` / `class_is_valuetype` / `class_value_size` 算好长度再读，
对加固版本依然不可靠。

**只允许两类操作**：① 已解析托管方法 + `runtime_invoke`；② 只读元数据枚举。

### 2) 调用托管方法前必须核对参数类型

用 `il2cpp_method_get_param` + `il2cpp_method_get_return_type` +
`il2cpp_class_from_type` + `il2cpp_class_get_name` 拿到真实签名。**不符就不调用。**

这条纪律拦下过必然的崩溃。实测纠正：

| 接口 | 错误假设 | 真相 | 后果 |
|---|---|---|---|
| `MarketingCameraController.ChangeFov` | float 增量 | **`System.Int32`** | 传 `-15.0f` 时位模式被当作 `-1047527424`，FOV 被巨大负速率拖成负数 → **画面全灰** |
| `CameraUtils.EnableDOF` | 传 float/bool | 需要 **`CameraDOFDescriptor` 对象** | 传浮点会按对象指针解引用 |
| `CameraManager.CreateOrGetTemporaryController` | 收 `Type` | 1 参重载收 **`UnityEngine.GameObject`** | 按 Type 传参会崩 |

### 3) 绝不在每帧数据流里做"对象查找"

`Resources.FindObjectsOfTypeAll(Type)` 会枚举**场景内全部已加载对象**，每次调用产生大量分配。
一旦挂在每帧数据流上（Blender 60 fps 推送），内存被迅速吃光 →
`[Critical] Commit memory failed` → 引擎崩溃（崩溃栈全是 `unityplayer`，不含本模块帧，
所以最难查）。

同类的 `Object.FindObjectsOfType(Type)` / `Object.FindObjectOfType(Type,bool)` 在本作
**要么返回 null、要么抛异常、要么刷 `FindAllObjectsOfType` 报错**，成本还极高。
**三者已从代码中彻底删除。**

任何"查找/枚举/遍历"只能由**显式指令**触发。

### 4) 改游戏状态的动作必须由用户显式触发

在标题画面自动调用 `ToggleSnapshotCamera` 之后，关卡加载阶段出现
`CameraManager.LoadPersistentController → CameraControllerBase.Init` 抛异常，
游戏**卡死在 loading 界面**。

所以：自举/探测阶段只做只读操作；进入拍照模式只能由显式指令（27 / `arm_lens.ps1`）触发。

### 5) 参数变化去重必须"先记录再尝试"

否则失败时每帧重试，既刷屏日志也可能拖垮进程。

### 6) 托管调用前必须把线程附加到 IL2CPP 域

`thread_attach(domain_get())`。未注册线程碰 VM 是
`fatal error in GC: Collecting from unknown thread` 的经典成因。

### 7) 帧内顺序决定写入是否生效

见第四节。**写位姿必须在 `CinemachineBrain.LateUpdate` 之后**；
**读引擎位姿必须在写入之前**（且只能用 Brain 钩子里的读数）。
