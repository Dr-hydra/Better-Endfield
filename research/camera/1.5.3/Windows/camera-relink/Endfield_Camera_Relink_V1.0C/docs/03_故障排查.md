## 1. 注入阶段

### 1.1 `CreateProcess 失败 err=740`

**原因**：注入器没有管理员权限，而游戏清单要求管理员。

**处理**：用 `tools\launch_game.ps1`（会自动弹 UAC 提权）。

### 1.2 `OpenProcess 失败 (err=5)`

**原因**：游戏已在运行且权限更高，无法打开它的句柄。

**处理**：不要用"运行中注入"。先退出游戏，用 `tools\launch_game.ps1` 做**挂起注入**。

### 1.3 日志停在 `il2cpp 未就绪, 缺失: GameAssembly.dll(模块未加载)` 不再前进

**原因**：注入成功但游戏没继续初始化（常见于直接拉起 `Endfield.exe` 而 ACE/启动器未就绪）。

**处理**：

```powershell
powershell -ExecutionPolicy Bypass -File tools\launch_game.ps1 -StartLauncher
```

先拉起启动器初始化 ACE，再注入。

### 1.4 游戏在 60 秒内退出，退出码 `0xC0000005`

**原因**：模块线程与 IL2CPP 的 `il2cpp_init` 初始化竞争，偶发踩坏内存。
崩溃栈特征：`il2cpp_init → il2cpp_class_from_name`，且**不含本模块帧**。

**处理**：模块已用保守等待规避（等 25 秒 + 静置 3 秒才碰 VM 接口）。
若仍遇到，**重试一次**；连续两次以上失败请看 `Player.log` 里崩溃前的报错，
并按 `02_其他电脑安装方案.md` 重建。

### 1.5 游戏窗口打不开、`Player.log` 长度为 0

**原因**：卡在启动前握手（ACE 未起来 / 启动器未跑过）。

**处理**：`-StartLauncher` 参数重跑；确认启动器本身能正常进游戏。

## 2. 武装阶段（`arm_lens.ps1`）

### 2.1 `marketing=0000000000000000`

**原因**：只发了指令 27 而没发指令 10。指令 9 只是"打印状态"，**不会去取实例**。

**处理**：用当前的 `arm_lens.ps1`（已修正顺序：27 → 2 → **10**）。
或手工：`tools\send_cmd.ps1 -Id 10`。

### 2.2 `snapshot=0000000000000000`

**原因**：在标题/加载画面下武装。拍照相机那时还没创建。

### 2.3 日志出现 `[lens] 光圈/对焦本次未应用: 快照相机实例未就绪`

**原因**：同上，实例未取到。

### 2.4 `ToggleSnapshotCamera` 返回 `ret=0000000000000000`

**原因**：拍照相机尚未创建（标题画面）。

实测提前调用会破坏关卡加载时的相机初始化，导致游戏**卡死在 loading 界面**。

## 3. 参数不生效

### 3.1 日志里完全没有 `[lens]` 行

**原因**：没有数据流入。可能是：

| 子原因 | 确认方法 | 处理 |
|---|---|---|
| Blender 没在发送 | 面板 `状态：` 不是"正在发送" | 点 `▶ 开始实时发送` |
| 两个 Blender 抢通道 | 面板看是否有多个 Blender 实例 | 只留一个，其余点停止 |
| 共享内存没连上 | 日志无 `共享内存已连接` | 确认游戏进程仍在运行 |

### 3.2 焦距/光圈只有其中一个生效

**原因**：通常是对应的 Blender 参数没打开。
对焦距离与光圈需要 **勾选 `Use Depth of Field`（启用景深）** 才参与。

### 3.3 光圈设了但虚化不明显

**依次检查**：

1. `Use Depth of Field` 是否勾选
2. F-Stop 是否够小（先用 1.4）
3. 对焦距离是否与画面主体同量级（设成几十米而主体在 3 米处 → 几乎全清晰）
4. 是否已 `arm_lens.ps1`（景深依赖拍照相机实例）

### 3.4 画面/焦距在两个值之间来回跳

**原因**：**两个 Blender 实例同时发送**。共享内存通道没有写入方标识，
两边各自的 `sequence` 都从 0 累加、互相碰撞，读端几乎每帧都判定为"新帧"，
于是两边参数被交替应用。

**处理**：只保留一个发送方，其余点 `⏸ 停止`。

### 3.5 刚进游戏 FOV 就跳到一个旧值

**原因**：共享内存映射是**持久**的，里面残留着上一轮最后一包，启动时被当成新帧应用了一次。

**处理**：无害，可忽略。想避免就先在 Blender 点停止，再进游戏。

## 4. 位置/朝向问题

### 4.1 移动 Blender 相机，游戏完全不动

**依次确认**：

1. `pose_mode` 是否为 3
   ```powershell
   tools\send_cmd2.ps1 -Id 35     # 看 relative= 和状态
   ```
   若不对：`tools\send_cmd2.ps1 -Id 22 -A0 3`
2. 是否在发送（面板状态）
3. 看诊断行：
   ```
   [diag:BrainLateUpdate] 写入前(引擎给出的值)=... | 目标=... | 写入后=...
   ```
   没有这行 → Brain 钩子没挂上，看日志里有没有
   `成功挂上 Cinemachine.CinemachineBrain.LateUpdate`

### 4.2 怎么动都不跟随（目标值一直不变）

**原因**：基线被高频重建，把位移"吸收"掉了。

**处理**：已修（只在断流 > 3 秒才重建）。若仍出现，手动重置一次基线再动：
```powershell
tools\send_cmd2.ps1 -Id 34
```

### 4.3 一开位置跟随画面就变虚空/发灰

**原因**：绝对坐标模式，或位移过大搬到关卡外。
相机位置本由游戏逻辑（角色位置、地形、碰撞）决定，强行搬到远处通常落进地形内部。

**处理**：

1. 确认相对模式开着：`game_mod\EndfieldCamLink.ini` 里 `pose_relative=true`
2. **位移控制在几米~几十米**，别用绝对值甩动
3. 立即恢复：`tools\send_cmd2.ps1 -Id 22 -A0 0`（关闭位置写入，相机交还游戏）
4. 重新对齐原点：`tools\send_cmd2.ps1 -Id 34`

### 4.4 相机卡在奇怪位置无法恢复

**原因**：数据流停了但还在写位姿（旧版本没有安全阀）。

**处理**：现在的版本有安全阀（断流 > 500ms 自动交还相机）。
若仍卡住：`tools\send_cmd2.ps1 -Id 22 -A0 0`，或退出重进游戏世界。

### 4.5 旋转不是标准直角坐标系 / 俯仰会歪 / 三轴互相串

**原因**：相对（增量）模式把 Blender 的**旋转增量**叠加到「游戏相机自己的基线朝向」上，
而两侧基线朝向天然相差一个常量角 Δ（现场实测 53.3°/89.0°，每次武装都不同）。
增量四元数只能左乘（世界系）或右乘（相机本地系），因此 **Δ≠0 时必然有一个系被 Δ 转过** ——
俯仰里混进滚转、或绕世界轴转时轴是斜的，操作起来就是「xyz 不是标准直角坐标系」。

**两枚硬币的两面（都在这里栽过跟头，都要知道）**：

| 增量算在哪个系 | 哪一侧是标准的 | 另一侧的实测偏差 |
|---|---|---|
| 世界系增量（1.0.0y 及以前写法的语义） | 绕 Blender **世界轴** 0.00°，且换姿态不漂移 | 绕相机**本地轴**偏 52.6~63.1°（俯仰带出滚转） |
| 本地帧增量（1.0.0z 起） | 绕相机**本地轴** 0.00° | 绕 Blender **世界轴**偏 38.8~76.9°（换姿态最大漂移 87°） |
| **Δ=0（把游戏基线对齐到映射后的 Blender 基线）** | **两侧同时 0.000°**（四种写法全部精确） | — |

**处理（v1.0.0at 及以后，推荐）**：相对模式的旋转改用**标准语义**（= 与绝对一致，
等价于武装时对齐基线 Δ=0），增量只作用在位置上；`pose_rot_increment_frame=0` 是默认值。

```powershell
tools\send_cmd2.ps1 -Id 38 -A0 1     # 绝对: Blender 全权决定朝向(两系同时一一对应)
tools\send_cmd2.ps1 -Id 38 -A0 0     # 相对: 按 ini 的增量系(v1.0.0at 默认 = 标准, 与绝对一致)
tools\send_cmd2.ps1 -Id 38 -A0 2     # 相对·世界系增量: 世界轴标准; 绕相机本地轴会带出滚转
tools\send_cmd2.ps1 -Id 38 -A0 3     # 相对·本地帧增量: 1.0.0z 语义; 绕世界轴会偏 Δ
```

**为什么"改 Blender 端坐标轴朝向"修不了**（2026-09-15 用户提案，已核对）：
1. 偏差**不是常量**：同一个"绕世界 X 转"在不同姿态下偏 38.8° / 65.7° / 76.9°，换基线最大漂移 87°。
   固定的轴重标（换轴/翻符号）只能产生**常量**偏差，因此改哪一端的固定轴约定都不可能对上。
2. Blender 端的轴约定正是"绝对映射两系同时 1:1"的成因；给它乘一个常量旋转，会把已经正确的
   绝对映射整体歪掉同样的角度 —— 修一个坏两个。
3. Δ 随每次武装变化（现场 89.0° → 53.3°），所以任何"把 Δ 写死进代码/写死进插件"的做法下次会话必然失效
   （v1.0.0z 已明确不做硬编码 Δ）。
4. 结论：这是**增量所在系**的选择问题，不是坐标轴约定问题；两系同时标准的唯一途径是 Δ=0。

**若是旧模块（1.0.0y 及以前）又必须用增量**：只能先切到绝对模式（`-A0 1`）规避，
或把模块换到 1.0.0z+（相对模式增量有本地帧/世界系/标准三种可选，见上）。

**怎么确认是不是这个问题**：看日志里的 `[map]` 行 ——
`朝向=...（与游戏基线朝向相差 X°）`，X 就是 Δ；**只有** `朝向=r相对·世界系/本地帧` 两种模式会受它影响。

完整数值对照（世界轴 / 本地轴 / 基线无关性 / Δ=0）：
`C:\Python314\python.exe source\tools\verify_rotation_mapping.py` 第 6 节。

**在线端到端对账（报"旋转不对"时先跑这个）**：`C:\Python314\python.exe source\tools\check_live_mapping.py`
—— 直接读共享内存里插件**正在发**的 `fwd/up`，独立复算一遍映射，再和模块从 transform **读回**的写入值比较；
差 < 0.5° 就说明"Blender 朝向 → 游戏相机朝向"这条链是精确的（剩下的是对语义的预期问题，不是映射错误）。

**关于数值符号**：Unity 左手系 / Blender 右手系，同一物理转向两边的欧拉角符号相反
（Blender 本地 X 正转 = 抬头；游戏里对应负角 = 同样抬头）。**以画面转向一致为准，
不要比对数字。**

### 4.6 位移方向不对

**原因**：Blender 与游戏的世界坐标轴映射不完全一致（Z-up/Y-up 轴交换 + 左右手系）。

**处理**：位置只做单轴小幅移动来确认方向；`pose_max_offset` 已做限幅保护。
需要逐轴校正请说明具体现象（哪个轴、正负哪边反），在 `source\src\link.cpp`
的相对换算段加轴映射即可。

### 4.7 相机没有按「方块相对位置」摆放（2026-09-10c）

**先跑诊断**：

```powershell
tools\send_cmd2.ps1 -Id 39
```

日志会打印：当前锚点 / 参考物件位置 / 本次位移 / 相机与角色相对位置。逐条对照：

| 现象 | 原因 | 处理 |
|---|---|---|
| `参考物件 pos=(0.00,0.00,0.00) hasRef=0` | 插件没带参考物件（场景里没有名为 `Cube` 的物体） | 在场景里放一个方块并**命名为 `Cube`**（v0.3.9 起参考物件固定用它，面板上没有开关了） |
| `参考物件` 数值不是你预期的方块位置 | 你的方块改名了；模块自动取的是名为 `Cube` 的物体 | 把方块改回 `Cube`（或把你自己的替身物体改名为 `Cube`） |
| 锚点显示"Blender相机基线(增量)" | 走了旧锚点 | `tools\send_cmd2.ps1 -Id 40 -A0 1` |
| 相机位置整体差一个固定量 | 游戏基线点是"武装那一刻相机的位置"，武装前你用游戏自己的相机挪过位置 | 重新武装一次（控制台菜单 [3] 武装相机） |

**原理**：游戏侧原点 = 武装那一刻游戏相机的位置（拍照模式下它就是"相机相对角色的位置"），
Blender 侧原点 = 参考物件。所以**方块摆在哪、相机相对方块怎么摆**就是游戏里的摆放。

### 4.8 Blender 相机在 (0,0,0) 时，游戏相机没压在角色身上（2026-09-10d）

**原因**：默认的"游戏侧原点"是**武装那一刻游戏相机的位置**，它和角色本身有少量偏差
（实测 `GetCameraOffset()` 返回 (0,0,0)，所以偏差不是"玩家手调的偏移"，而是相机与角色的固有差）。

**处理（二选一）**：

**① 一次性校准**（推荐先试）：

```powershell
tools\calibrate_origin.ps1
```

1. 把 Blender 相机位置设为 `(0,0,0)`
2. 用 Blender 把游戏相机挪到正好与角色重合
3. 运行上面的脚本（= 指令 41）
4. 把 Blender 相机位置设回 `(0,0,0)` → 现在正好落在角色身上

> 第 3 步瞬间画面会跳一下（原点即刻生效），第 4 步回到你刚对准的位置；
> 日志 `[origin]` 行会打印修正量，写进 ini 的 `pose_origin_dx/dy/dz` 可跨会话保留。

**② 直接取角色锚点**：

```powershell
tools\send_cmd2.ps1 -Id 43            # 打印 4 个候选的坐标与解析情况
tools\send_cmd2.ps1 -Id 42 -A0 1      # 选一个看着落在角色上的(1=vcamFollow 最常见)
```

### 4.10 一武装相机就自己转了一下

**这是 2026-09-10c 起的有意行为**：武装脚本会通知插件执行「相机水平归零」
（保留水平朝向角，俯仰/滚转归零），让基线姿态与地面水平、便于操作。

**不想这样**：插件面板里取消勾选「武装时自动水平归零」。
**注意**：相机旋转带关键帧时，归零结果会在下一帧被动画覆盖（属于预期）。

### 4.11 之前对好的相机，重开一次武装后 (0,0,0) 又不落在角色身上（2026-09-11 实测）

**先看两个数**：日志里 `[map]` 行的 `游戏基线点`（本次武装的原点）和上一次武装的那个值。

`pose_origin_dx/dy/dz` 是**世界系固定向量**，它记录的是"原点 → 角色"的差。
一旦原点变了，同一个修正量自然落不到角色身上。实测就发生过：

```
上一次: 游戏基线点 = (-177.38, 263.35, 582.64)  →  角色点 = 基线 + Δ
本次  : 游戏基线点 = (-179.14, 263.19, 582.14)  →  原点挪了 1.84 m
          (新时序里的"复位自由相机位置"(指令 21) 把这个点换了)
结果  : (0,0,0) 落点差了 1.84 m —— 不是映射错了, 是校准量过期了
```

**判断方法**：新 `[map]` 原点 − 旧 `[map]` 原点 就是现在偏差的量级；
`[diag]` 里"写入前(引擎给出的值)"始终等于本次原点 → 说明是原点变了，不是写入被污染。

**修法（两条，推荐第二条）**：

1. 重新校准一次（把 Blender 相机放回 `(0,0,0)`，用 Blender 把游戏相机挪到角色上，
   跑 `tools\calibrate_origin.ps1`）。适用于原点每次武装都变的情形。
2. **自动校准**（v1.3，不需要肉眼对齐）：
   ```
   tools\send_cmd2.ps1 -Id 42 -A0 <1..4>    ; 选定角色锚点来源(先看 43/46 的输出)
   tools\send_cmd2.ps1 -Id 41 -A0 0 -A1 1   ; 修正量 = 锚点 − 武装点, 每次武装都可重来
   ```
   之后把日志打印出来的 `pose_origin_dx/dy/dz` 填进 ini 即可持久化。

**想少一次麻烦**：`tools\arm_lens.ps1 -NoReset` 跳过复位（原点就取自由相机当时停的地方，
更容易与上次一致）。

### 4.12 用探测轮找"角色位置"（指令 44/45/46，v1.3）

一键脚本：

```powershell
powershell -ExecutionPolicy Bypass -File tools\probe_b.ps1
```

它依次发 27（取快照相机实例）→ 2（开自由相机）→ 44（类型体检）→ 46（候选采样）
→ 45（写入-测量），并把相关日志片段存成 `game_mod\probe_b_report.txt`。

| 现象 | 含义 / 下一步 |
|---|---|
| `[audit]` 里某个 getter `声明=` 与 `实际=` 的类名都对不上 | 那个对象不是该类型的实例，对应候选不可用（v1.3 起校验改按类名比对父类链） |
| `[probe46]` 某候选 极差 > 0.02 | 该候选在动（角色待机微动是几厘米；大数值多半只是相机相关量） |
| `[probe46]` 某候选 距引擎相机 ≈ 0 | 它是相机自身，不能当角色锚点 |
| `[probe45]` 出现「结论: 约定…可用」 | 这条路通，那一行的 锚点(x,y,z) 就是角色位置 |
| `[probe45]` 两种约定都「未生效」 | 当前激活相机不是快照相机，或偏移只在编辑态生效 → 换 B1 路线（vcam Follow） |

**安全说明**：45 会真的写游戏相机偏移，结束时写回 `(0,0,0)`；探测期间位姿写入自动关闭，
结束自动恢复。若相机被写到意外位置，发指令 21（复位自由相机位置）即可恢复。

**实测经验（2026-09-11，两遍探测）**：

| 现象 | 原因 / 处置 |
|---|---|
| 45 两种约定都"未生效"，读回始终 `(0,0,0)` | **当前激活相机是官方自由相机**。`get_curActiveController` = `MarketingCameraController`，快照控件的偏移管不到它 → 先发指令 3 关掉自由相机，或跑 `probe_b.ps1 -NoFreeCam` |
| 装箱约定无效果、裸值指针有效 | 值类型参数的两种调用约定里，本作是**裸值指针**（装箱不报错、只是什么都不做）—— 判据是"读回值是否等于最后写入的值" |
| `[audit]` 说 `get_curVirtualCam` "实际类与声明对不上" | 声明类型是**接口** `Cinemachine.ICinemachineCamera`，接口不在父类链上 —— 1.0.0i 起改为按 `Follow/LookAt` 的**方法所属类**校验，候选 1/2 即可用 |
| 46 里 `controllerTrans` / `camMinusOffset` 距引擎相机 = 0 | 它们就是相机自身（偏移为 0 时），不能当角色锚点 |
| 46 里引擎相机极差 = 0.00000 | 拍照模式下机架是静止的（待机呼吸也看不到）；**"是否跟随角色"必须让角色真的走动才能验证** |

### 4.13 进干员/角色界面后，相机对不上界面里的角色（2026-09-15 已修）

**现象**：世界里跟随正常，一进干员界面（或其他"UI 里摆着角色模型"的界面）相机就跑到别处；按
控制台菜单 [6] 重新对齐位置原点（重置基线）也没用 —— 以前某个版本按一下就能重新找到角色。

**根因（两层）**：

1. **界面里读不到世界角色的锚点**：进入该类界面后 `vcamFollow` 实时读取失败，模块退回**粘性缓存值**；
   实测那份缓存是 **211 秒前**的值，与当前引擎相机相差约 **709 米** —— 相机原点就停在三分钟前的位置。
2. **旧代码把缓存值当成有效原点**：`GameSysAnchorPosition()` 在实时读失败时**返回 true 并附上缓存值**，
   于是 `if (srcOk && GameSysAnchorPosition(...))` 判定成功、兜底扫描永远走不到。
   而"重置基线"（指令 34 → `CapturePoseBaseline()` → `LatchAnchor()`）**确实会重新抓锚点**（与旧版逐行
   一致），但抓的还是同一个读不到的源 → 所以按了也没用。

**已修（1.0.0ap）**：锚点来源**自动回退** —— 首选仍是 `vcamFollow`；一旦它"读到的不是新鲜值"，
自动改用**引擎相机**（游戏自己的机位，永远可用；干员界面里它正看着 UI 里的角色），
抓锚点与每帧取原点都如此；恢复可读后自动切回。滞回 0.5 秒 / 0.3 秒，避免单帧失败来回跳。

**日志**：

```
[anchor] 自动回退: 首选来源 vcamFollow 读到的是缓存值(不新鲜) → 本次冻结改用**引擎相机**
[anchor] 自动回退: 首选来源连续 0.5 秒读不到新鲜值 → 改用**引擎相机**(原点=游戏机位)…
[anchor] 自动恢复: 首选来源重新可读 → 切回该来源(不再用引擎相机)
```

**相关命令**：

```powershell
tools\send_cmd2.ps1 -Id 72 -A0 0   # 关掉自动回退(回到旧行为: 读不到就沿用缓存值)
tools\send_cmd2.ps1 -Id 72 -A0 1   # 重新开启(默认)
tools\send_cmd2.ps1 -Id 42 -A0 5   # 手动: 直接用引擎相机当原点(干员界面的"稳"选择)
tools\send_cmd2.ps1 -Id 43         # 只读: 看全部候选(哪个实时可读、离引擎相机多远)
```

**代价**：回退期间原点语义变成"游戏机位"（不叠加锚点微调量 `pose_anchor_o*`），切换瞬间构图可能跳一下；
想完全避免就用 `-Id 42 -A0 5` 手动固定为引擎相机。

> 为什么界面里的角色找不到：它很可能是 **UIModel（层 13）** 的独立模型（`GetUIModelLayerMask` 含位 13），
> 由 UI 相机渲染 —— 不在世界坐标里，所以任何"世界角色锚点"都指不到它。

## 5. 脚本/控制台自身的问题

### 5.1 运行某个 .cmd 时报 `Missing closing ')' in expression` / `Missing argument in parameter list`

**原因**：该 `.ps1` 没有 **UTF-8 BOM**。PowerShell 5.1 读取无 BOM 的 `.ps1` 时按系统
ANSI 代码页（中文系统 = GBK）解码，中文被误码，某些字节组合会把引号或括号「吃掉」→
整个脚本解析失败，**一条指令都发不出去**（模块日志不会有任何新行，这是最典型的特征）。

**处理**（2026-09-10b 已修）：把该 `.ps1` 保存为 **UTF-8 带 BOM**。核对方法：

```powershell
Get-ChildItem .\install\*.ps1,.\tools\*.ps1 | ForEach-Object {
  $b=[IO.File]::ReadAllBytes($_.FullName)
  "{0,-28} BOM={1}" -f $_.Name, ($b[0] -eq 0xEF -and $b[1] -eq 0xBB -and $b[2] -eq 0xBF)
}
```

全部应为 `BOM=True`（包内 14 个脚本现已全部带 BOM）。
`.cmd` 包装器则是**纯 ASCII**，不含中文，避免同一类问题。

### 5.2 界面中文显示成乱码

同上：该 `.ps1` 缺 BOM。补上即可。

### 6.1 日志文件疯长

**原因**：某个每帧路径在刷日志（历史版本出现过：未武装时每帧尝试获取实例）。

### 6.2 游戏内存持续上涨直到崩溃

**现象**：`Player.log` 里出现
`[Critical] Commit memory failed, error code is: 0x1000000`，
崩溃栈全是 `unityplayer`（不含本模块帧）。

**原因**：历史上是"每帧枚举场景对象"导致的（`Resources.FindObjectsOfTypeAll`）。
**现行版本已彻底删除该调用路径**。

**处理**：确认用的是包内现行 DLL；出现该现象立即停止使用并把日志交回。

### 6.3 `fatal error in GC: Collecting from unknown thread`

**说明**：这个错误在本作**未装任何模块时也出现过**
（游戏目录 `Endfield.gc.log` 的创建时间早于本项目）。

**现行缓解措施**：模块自举线程在启动后静置，且一拿到 IL2CPP 域就立刻
`thread_attach` 注册进 GC。

**处理**：重试。若频繁出现请提供 `Endfield.gc.log` 与模块日志。

### 6.4 【随角色】模式下释放终结技→游戏崩溃（1.0.0av 曾修，**2026-09-18 已随该系列一并回退**）

> ⚠ **本节与 6.5 描述的修复已从代码中回退**（用户判定"改动过于复杂"，要求回到修崩溃之前的 1.0.0at；
> 详见 `VERSION.txt` 的"本次回退"条目）。**症状与取证分析仍然有效**，保留作为下次重做的依据；
> 但下面这些开关/指令在当前版本里**不存在**。临时规避依旧是：拍摄用【定镜头】。

**现象**：面板选【随角色镜头】时，释放终结技（或任何会切换虚拟相机的过场/切镜）会让游戏崩溃；
【定镜头】不崩 —— 因为每帧探锚点候选的代码只在【随角色】分支里（`link.cpp` 的 `if (followMode)`）。

**崩溃栈**（四次完全同形）：
`游戏 Tick / Brain 帧末 → ApplyPoseTarget（写入时刻补读）→ GameSysAnchorPosition/AnchorPositionLive
→ TransformPos → il2cpp_runtime_invoke → UnityEngine.Transform.get_position → 崩在 unityplayer 内部`。
（崩溃报告里的符号名是“最近导出符号”猜出来的，**不可信**——例如 `ApplyShmemLens` 实际是 `ApplyPoseTarget`；
要认函数请用 PE 异常目录（`.pdata`）切出边界后再看它引用的字符串。）

**根因**（逐帧取证定案，详见 `VERSION.txt` 的 1.0.0au / 1.0.0av 条目）：
终结技在**同一帧内**换掉 vcam；位姿路径读到的还是旧 vcam，而“写入时刻补读”取到了**新** vcam 的 Follow，
对它调 `Transform.get_position` → 游戏当场死。关键：崩前那一行显示该对象 **存活=1**（Unity 自己的
`IsNativeObjectAlive` 说它活着），且全程没有任何托管异常 ⇒ **存活判定与异常保护都挡不住**；
可用信号只有“**对象指针变更**”。

**修复**（v1.0.0av 系列，最终四项）：
0. **冷静期只管"刚出现的对象"**（最终 30ms ≈ 1~2 帧）；任何**指令与武装时的锚点冻结都豁免**它（否则武装选不到角色 → 原点错位）。
   兼底扫描已**剔除 controllerTrans**（实测它就是 `Camera.main` 的 transform），且冷静期跳过时**不再下探**（否则会落到候选 4＝相机派生的原点，鼠标会串进来）。
1. 锚点对象**冷静期**：刚出现的 `vcam` / `vcam.Follow` / `controller` 在 `pose_anchor_settle_ms`（默认 500ms）
   内**一律不调它们的引擎 getter**，该来源按“读不到”处理 → 黏性缓存/自动回退接管
   （与今天遇到读失败时的行为完全一致）。
2. **失败退避**：某来源读失败后 `pose_anchor_error_backoff_ms`（默认 500ms）内不重试，避免每帧
   都去戳已经坏掉的相机 API（实测单会话可刷出 6936 条 `get_curVirtualCam` 抛异常）。
3. **写入时刻的补读默认不再读“对象来源”**（vcam/controller），只用无对象来源（4/５）补读；
   对象来源沿用本帧已算好的锚点（代价：走动时约一帧滞后）。

**开关**（`game_mod\EndfieldCamLink.ini`）：`pose_anchor_settle_ms` / `pose_anchor_error_backoff_ms` /
`pose_late_anchor_object_sources`。任一设 0（或 false）即回到旧行为。
**临时规避**（修复前或不想用新版）：面板用【定镜头】——实测不崩。

**下次还出事怎么取证**：`tools\send_cmd2.ps1 -Id 79`（对象链存活体检）
+ `tools\send_cmd2.ps1 -Id 80 -A0 120`（逐帧追踪，输出 `game_mod\EndfieldCamLink_camprobe.log`，
**每行都落盘，崩溃也不丢**）。看文件尾部即可：
`A-pre src=.. tgtA=<0/1> thr=<异常计数>`（调 getter 前的快照）、`F.. CM/CA/CTr/CTA/CC/MK/SN/AN/AL`（每帧）、
`#chain ..`（每秒：锚点链上每个对象的 指针/存活/是否抛异常）。

### 6.5 【随角色】相机"钉住/变成定镜头"（fix7～fix9 曾修，**2026-09-18 已随该系列一并回退**）

> ⚠ 本节描述的 fix 已在同一次回退中移除（当前版本 = 1.0.0at，无 `pose_anchor_freeze_object` /
> `pose_ride_on_scene_jump` / `pose_official_camera_ride` / 指令 81 / `[ride]`·`[watch]` 日志）。
> 下面的**现象、根因与判据数据**保留，作为下次重做的起点。

**现象（两个，都是 6.4 修好后暴露出来的）**

1. **游戏换场景后相机留在旧世界**（打完一局回到编队界面、进终结技运镜等）。
   用户原话："完全乱了，现在角色跟随模式在不进入官方相机的情况下直接变成定镜头了。"
   日志实况：`[diag] 引擎相机位置单帧突变 726.8 米: (-56.17,201.62,504.85) -> (-200.18,300.83,-200.56)`，
   之后 10 分钟里冻结的角色锚点停在 (-63.22, 200.51, 503.46)（旧战斗世界），引擎相机静止在
   (-198.68, 302.23, -196.38)（编队界面），两者相距 720 米 → 目标恒定不变。
2. **进官方相机（拍照模式）后相机不动**。用户原话："大部分是正确的，但是目前进入官方相机后变成了定镜头。"
   日志实况：进官方相机时引擎相机从 (-66.59, 203.81, 512.31) 跳到 (-8.21, 2.14, 0.00) ——
   游戏把角色搬进**世界原点附近的影棚场景**；影棚里引擎相机 ≈ (-4.55, 2.10, -6.47)、
   角色锚点 ≈ (-4.55, 0.14, -3.61) 且**一动不动**（角色是摆好的静止主体），目标恒定 (-3.31, 0.80, -7.50)。

**根因（一条主线，三层）**

- **为什么之前会崩 → 最终判据是"永远只读同一个对象"（fix7）**。
  6.4 里的冷静期/白名单/缓存都被实战打穿：新运镜对象的 Follow 会被**成功读过一次**（用户能看到终结技首帧），
  于是进了白名单；缓存则会在过期或读失败时回到"实时查 vcam"。
  现在的规则：**只在一次性路径（武装建立基线 / 指令 49 / 面板切换）里认下一个 Transform 并冻结**，
  之后每帧只读它、不再调 `get_curVirtualCam`/`get_Follow`、不按时间刷新、读不到也不改指
  （沿用上一个值 + 提示重新武装）。日志 `[anchor] 已冻结锚点对象(vcamFollow): ptr=…`。
- **为什么修完会"钉在旧世界"（fix8）**：冻结对象在游戏换场景后留在旧场景，而游戏相机已经走了 700+ 米。
- **为什么进官方相机会"钉住"（fix9）**：影棚里的角色是**静止主体**，"原点取角色坐标"就等于把相机钉住；
  而官方相机里玩家操作的**恰恰是游戏相机**。

**修法（全部只读"引擎相机位置"或"已冻结的那一个对象"，不碰新对象 ⇒ 不引入崩溃风险）**

| 版本 | 判据 | 动作 | 开关 |
|---|---|---|---|
| fix7 | 一次性路径里成功读到对象 | 冻结该 Transform，此后每帧只读它 | `pose_anchor_freeze_object` |
| fix8 | 引擎相机单帧位移 > 30 米，或距角色锚点 > 150 米持续 1 秒 | 原点改用**游戏相机**（骑乘） | `pose_ride_on_scene_jump` |
| fix8 | 引擎相机回到锚点附近 < 80 米持续 0.8 秒 | 切回**角色锚点** | 同上 |
| fix9 | 引擎相机距世界原点 < 60 米（影棚/官方相机态） | 原点改用**游戏相机** | `pose_official_camera_ride`；指令 81 热切 |

指令 81：`-A0 1` 官方相机态骑游戏相机（默认）/ `-A0 0` 仍用角色锚点（旧行为）/ `-A0 2` 回到 ini。

**日志怎么读**

- `[anchor] 已冻结锚点对象(vcamFollow): ptr=… 值=(…)` —— 冻结通道生效（武装/指令 49 时出现）。
- `[watch] 冻结锚点(vcamFollow) … 引擎相机=(…) 间距=x 米` —— 1 Hz 观察行；正常情况下间距≈Blender 偏移。
- `[diag] 引擎相机位置单帧突变 x 米` —— **游戏换场景/进运镜的免费现场标记**（这条链不读任何对象）。
- `[ride] …` —— 骑乘进/出；官方相机态下每 3 秒一条 `curActiveController 类名=…`
  （若类名里出现 `Snapshot`，说明"官方相机态"有语义判据，可以换掉现在的坐标判据）。
- `[anchor] 冻结的锚点对象(vcamFollow)读不到(…)` —— 冻结对象失效（多半是换场景/换角色），
  此时**重新武装**或发指令 49 才会重新认对象；平时不会自动改指。

**已知代价**：换场景后冻结的角色对象会失效，要靠"重新武装/指令 49"重新认；
骑乘期间相机跟着游戏相机走，鼠标会串进位置（这是官方相机里的预期行为，正常游玩不受影响）。

## 7. 完全没反应时的通用流程

**最省事的做法：双击 `相机控制台.cmd`**，它顶部会显示游戏/Blender/管理员状态，然后依次用：

```
[8] 查看相机状态        ← 先看这里, 会提示"实例是否就绪"或"本次不是用本包启动的"

[5] 查看运行日志        ← 看日志尾部找原因
```

想手工排查就按下面顺序：

```powershell
cd <包目录>\EndfieldCameraLink

Get-ChildItem game_mod\EndfieldCamLink.log
Get-Content game_mod\EndfieldCamLink.log -Tail 40 -Encoding UTF8

# 2) 游戏进程是否还活着
Get-Process Endfield

# 3) 接收端是否就绪（9=状态, 10=刷新实例, 35=位姿基线）
tools\send_cmd.ps1  -Id 9
tools\send_cmd.ps1  -Id 10
tools\send_cmd2.ps1 -Id 35

# 4) 重新武装一遍
powershell -ExecutionPolicy Bypass -File tools\arm_lens.ps1
```

还不行就整体重启（`-ForceKill` 会结束残留游戏进程，受 ACE 保护的进程需要管理员权限，
脚本会自动提权）：

```powershell
# 双击「2-启动游戏并注入」，或：
powershell -ExecutionPolicy Bypass -File tools\launch_game.ps1 -ForceKill
```

> 「游戏在运行，但本包没有日志 —— 本次游戏不是用本包启动的」，
> 说明模块没被注入（例如你从启动器直接点了开始游戏）。
> 必须退出游戏后用 [2] 重新启动。

## 9. 高强度运镜时画面抽动（跟随模式最容易碰到）

### 现象

- 慢速/小幅运镜一切正常；**运镜幅度一大（快速摇臂、猛推拉、环绕加速）就出现"抽动/一顿一顿"**。
- 看起来是**整帧级别的跳**（不是逐帧微抖），跟随模式（随角色）比定镜头更容易碰到。
- 把运镜速度降下来、或者让相机停住，现象就消失。

### 原因（已实测确认）

**发送频率不足。** 这条链路是"**按有没有新包来写**"的：

```
CinemachineBrain.LateUpdate（游戏先把相机摆成它自己的位姿）
        ↓
我们的钩子：ApplyPoseTarget()
        ↓
ShmemLatest() 发现"没有新包" → 整个函数 return（既不写位姿，也不读锚点）
        ↓
这一帧渲染出来的是【游戏自己的相机位姿】—— 不是我们要拍的那个机位
```

- 所以"**没有新包的帧**" = 一帧回跳到游戏相机（角色后上方约 3.4 m 的常规机位）。
- **回跳幅度 = |我们的目标 − 游戏相机位姿|**：运镜幅度越大两者差得越远 → 跳得越明显。
  这正是"只有高强度运镜才抽动"的原因。
- 包率只要**低于或等于**游戏帧率，就必然有帧拿不到新包：发送是**自由运行的定时器**，
  与 Blender 的帧推进、与游戏的渲染帧都不同步，相位漂移 + 定时器抖动 = 稳定地漏帧。

### 处理

**把面板的「发送频率」拉到 240 以上。** 规则是 **≥ 游戏帧率的 2 倍**：

| 游戏帧率 | 发送频率 |
|---|---|
| 120 fps | **240**（实测够用）；要留余量可到 360~480 |
| 60 fps | 120 以上 |

实测记录：从 120 提到"360"（当时插件 ≤0.3.6 的硬上限是 240，因此**实际生效 240** —— 属性上限与
`_timer` 各夹一次）之后，跟随模式下的抽动消失。

> **上限已放开**：插件 **0.3.7** 起 `发送频率` 的上限是 **1000**（旧版是 240），现在填 360 就真的是 360。
> 但要注意上限只是"允许设到多少"：Blender 定时器由 UI 事件循环调度，1000 Hz（1 ms）**实际达不到**，
> 面板值只是目标值；而且包构建成本随频率线性上升。**240~480 是实际可用的区间，不是越大越好。**
> 调高包率**几乎不增加游戏侧开销**：模块每个渲染帧只读一次共享内存，多出来的包只是被覆盖。

### 如果已经 ≥2× 游戏帧率仍然抽动

按下表逐条自查（每条都能独立判断方向）：

| 检查 | 说明 |
|---|---|
| 角色静止、只有相机高速运镜时还抽吗？ | 还抽 → 与锚点无关，仍属包率/采样相位方向；不抽 → 看下一条 |
| 日志里搜 `缓存年龄` | 出现 `[anchor] … 实时读取失败, 改用缓存值(…), 缓存年龄 x.x 秒` → 锚点在"实时值"和"旧值"之间逐帧跳变 |
| 抽动是否与跑动/攻击节奏同步 | 是 → 锚点取的是角色根节点，跑动的上下起伏与攻击/闪避的 root motion 被相机一起继承了 |
| 定镜头下做同样强度的运镜呢 | 也抽 → 与锚点无关（仍是包率/采样相位）；只有跟随模式抽 → 跟随模式特有的问题 |

### 根因层面还没做的事（记录备查）

"按有没有新包才写"是**边缘触发**，本质应改成**电平触发**：每帧都用"最近收到的包"重写位姿
（只要还在 500 ms 安全窗口内）。这样丢包只会让画面**保持上一帧姿态**，而不会露出游戏自己的相机位姿 ——
做到那一步后，低包率也不会再抽动。当前采用的是**提高包率**这个成本最低、已验证有效的开关，
电平触发留作后续可选改进。

## 9b. 随角色模式下"角色走动/跳跃时的小幅抖动"（v1.0.0ab）

### 现象（与 §9 的区别要分清）

| | §9（漏帧型） | §9b（锚点型） |
|---|---|---|
| 触发 | **相机运镜幅度**大 | **角色移动**（走动/跳跃） |
| 幅度 | 整帧级别的回跳（米级） | **小幅度**，且**随角色速度增大** |
| 角色静止 | 仍可能抖 | **不抖** |
| 定镜头（冻结锚点） | 仍可能抖 | **不抖** |
| Blender 相机完全不动 | 不抖 | **照样抖** |
| 与步频 | 无关 | 无关 |

如果符合右列，那就是**锚点这一路**的问题，继续加发送频率没有用。

### 原因

目标位置 = **锚点** + Blender 位移。我们贴的是**角色侧节点的原始位置**，
而游戏自己的相机是**逐帧平滑 + 带跟随阻尼**的 —— 我们把那一层丢掉了，
于是锚点的时间粒度/相位差异直接变成"相机相对角色"的小幅抖动。

### 处理：把原点换成"引擎相机"（3 号方案，v1.0.0ab）

```powershell
tools\send_cmd2.ps1 -Id 42 -A0 5     # 原点 = 游戏当前机位(带游戏的平滑/阻尼) + Blender 偏移
tools\send_cmd2.ps1 -Id 42 -A0 1     # 不合意就切回 vcamFollow(角色脚底锚点)
tools\send_cmd2.ps1 -Id 42 -A0 0     # 或切回"武装点"锚点
tools\send_cmd2.ps1 -Id 43           # 打印全部候选坐标, 确认当前来源
```

- 语义变成"**以游戏当前机位为原点，只叠加 Blender 位移**"：Blender 相机放在参考物件上 = 与游戏机位重合，
  之后再从那里加偏移。
- **不叠加锚点微调量**（`pose_anchor_ox/oy/oz`，那是"脚底→头部"用的）—— 想微调就直接移动 Blender 相机。
- **硬前提**：游戏相机本身确实在跟随角色。若切过去发现"角色走开、画面不动"，说明当前状态下
  游戏相机是静止的（例如拍照模式的快照相机）→ 该方案在此状态下等价于定镜头，切回 1 即可。
  判定方法：`-Id 46 -A0 600` 采样时看**「引擎相机」那一行的极差**（米级 = 在跟随；≈0 = 静止）。
- 与 §9 的"抬高发送频率"不冲突，两者可以同时用。

## 9c. 逐帧追踪：定位"角色走动时的小幅抖动"到底来自哪一环（v1.0.0ad）

### 为什么要它

实测结论（2026-09-14）：把原点从"角色锚点"换成"**引擎相机**"（§9b 的 3 号方案）之后，
**抖动依旧存在**，只是多了一个"相机被角色与相机之间的障碍物影响"的副作用
（那是游戏相机管线里的**遮挡回避**，正好说明来源 5 让我们骑上了游戏自己的相机管线）。
→ 说明抖动**不在"原点够不够平滑"这一层，而在逐帧的位置信号本身**。
60 帧一次的 `[diag]` 看不到逐帧细节，所以加了按帧输出的只读追踪。

> 副作用提示：**来源 5（引擎相机）会继承游戏的遮挡回避**，想避开就切回
> `tools\send_cmd2.ps1 -Id 42 -A0 1`（vcamFollow）。

### 怎么用

```powershell
tools\send_cmd2.ps1 -Id 60 -A0 1200     # 开始逐帧追踪(1200 帧 ≈ 10 秒 @120fps)
# 然后让角色走动 + 跳跃约 10 秒
tools\send_cmd2.ps1 -Id 61              # 提前停止(帧数用尽也会自动停)
python source\tools\analyze_trace.py    # 分析(纯 Python, 只读日志)
```

`[tr]` 每行长这样（字段：帧序号/时间/距上帧毫秒、引擎相机、本帧原点与来源、
vcamFollow 读数、写入目标、写入后回读、朝向、包序号与 Blender 帧号）：

```
[tr] n=41 t=1234567 dt=8 | eng=(105.76,169.23,504.15) | org=(110.40,168.69,506.58) src=vcamFollow | anc=ok(110.40,168.69,506.58) | tgt=(109.21,167.93,494.02) | post=(109.21,167.93,494.02) | rot=(...) | pkt seq=812 bf=406
```

### 分析器给出的判据

| 观测 | 结论 | 方向 |
|---|---|---|
| **引擎相机**在"目标在动"的帧里成片**零步长**（保持不动再跳一格） | 游戏相机本身是**阶梯**（固定步长/更新粒度） | 对位置做**亚帧插值**（把"保持"补成"斜坡"），或换更细粒度的来源 |
| **vcamFollow** 成片零步长 | 角色侧节点是阶梯 | 换锚点节点 / 平滑锚点 |
| 各信号都在逐帧变化，但"步长÷帧时间"的速度序列抖动大 | **时间相位 / 帧时间抖动** | 对齐时间基准；必要时对相机做插值 |
| 包序号大量重复、Blender 帧号重复多 | Blender 侧采样与帧推进不同步 | 见 §9（发送与帧率关系） |
| `|目标 − 写入后回读|` 明显不为 0 | 写入没生效（有别人在我们之后写相机） | 查写入时机 |

建议**跑两次**对照：`-Id 42 -A0 1`（vcamFollow）一次、`-A0 5`（引擎相机）一次 ——
两次的差异能直接指出"哪条通路更干净"。

### 9d. 实测结论（2026-09-14）：相机用的角色坐标**稳定落后一次调用**，而调用间隔在抖

2400 帧逐帧追踪（指令 60）的逐行检验结果：

| 检验 | 结果 |
|---|---|
| 本帧原点用到的锚点 == **上一行**记录到的锚点 | **2410 / 2410 行** |
| 本帧原点用到的锚点 == 本行的锚点 | 0 行 |
| 写入目标 == 写入后回读 | 2411 / 2411 行（写入本身没问题） |
| 引擎相机 == vcamFollow + 常量 | 逐行成立（游戏相机刚性跟随角色） |

```
相机与角色的相位差 = v(角色速度) × (调用间隔的抖动)   →  幅度 ∝ 速度；静止为 0
```

这与全部现象吻合：走动/跳跃才抖、幅度随速度、与步频无关、站立不抖、**定镜头不抖**、
Blender 相机不动也抖。也解释了**为什么换来源 5（引擎相机）没用**：来源 5 读的是同一层的值，同样晚一拍。

**验证开关**：

```powershell
tools\send_cmd2.ps1 -Id 62 -A0 1     # 写入前补读锚点(把目标补到最新)
tools\send_cmd2.ps1 -Id 62 -A0 0     # 关闭(默认)
```

打开后抖动若消失/明显减小 → 根因确认；若不变 → 差距在"写入与渲染之间"，
下一步在追踪里对比"上一帧写入后回读"与"本帧引擎相机"，判断是否有别的步骤在我们之后又写了相机。

追踪行里的相关字段（指令 60 期间才有）：

```
ancU=L/C(x,y,z)   原点实际用到的锚点, L=实时读到 / C=退回粘性缓存
now=ok(x,y,z)     本行末尾再读一次的锚点
live=0/1          上面那次是否实时
late=0/1 err=米   补读开关状态 / |ancU − now|(即"落后量")
```

## 9e. 根因与永久修法（2026-09-14 定案）

> **先更正 9d**：9d 的"落后一整拍"由**第一版探针**测出，而那版探针每帧写日志，
> 日志 I/O 恰好夹在两次锚点读之间 → 结论被观测者效应污染；据此实现的补读还把抖动弄得更严重。
> 下面的结论来自 **1.0.0af 的零 I/O 探针**（循环内只写内存、结束时一次性落盘）。

### 根因：原点在**帧内早期**读，相机在**帧末**写

```
帧内:  TailLateTick 组   OnGameTick: 读锚点 → 算目标(g_target)   ← 原点在这里定型
             ↓  ← 角色在这里继续更新(大半个帧)
       Brain.LateUpdate 之后  ApplyPoseTarget: 写进相机 → 渲染
```

零 I/O 逐帧追踪（走动段 1471 帧）实测：

| 检验 | 结果 | 含义 |
|---|---|---|
| `\|a1 − a2\|`（调用开头连续两次读、中间零工作） | **0.0000 m（100%）** | 锚点在一次调用内不变 → **无并发竞态** |
| `\|aU − a3\| / 位移` | **1.000** | 目标用的锚点比"写入时刻读到的"**整整旧一个相位** |
| `dtUs`（走动时） | 中位 ~20 ms、p90 24 ms、最大 **49 ms**、**37% 的帧偏离中位 >20%** | 帧时间本身在抖 |

→ **相位差 = 角色速度 × 帧时间**：帧时间一抖，画面里的相对偏移就抖。
这解释了全部现象：**幅度 ∝ 速度**、只有走动/跳跃出现、静止与定镜头（冻结锚点）都不出现、
与步频无关、换锚点来源（引擎相机）或加发送频率都无效。

### 修法（v1.0.0ah 起**默认开启**，永久生效）

写入前重读同一来源的锚点并补差：

```
p += 锚点(写入时刻) − 锚点(算目标时)
```

实测 `|补读值 − 写入时刻读到的锚点| = 0.0000 m`（1471 个移动帧，
而补读前的同一比较是 1.000 个相位），主观评价"完美解决"。

```ini
; game_mod\EndfieldCamLink.ini —— 默认值
pose_late_anchor=true        ; 要关掉写 false
```

运行时开关：`tools\send_cmd2.ps1 -Id 62 -A0 1`（开）/ `-A0 0`（关）。
代价：每帧多一次锚点读取（3 次只读反射调用），实测帧时间无可见变化。

### 这次排查留下的两条教训

1. **探针本身会改变被测量**：第一版"逐帧追踪"每帧 `snprintf` + 写文件，这段 I/O 夹在两次
   锚点读之间，把"两次读之间的时间"拉长到毫秒级，于是测出了"正好落后一整拍"的假象。
   **测量必须在测量循环里零 I/O**（内存缓冲 + 结束时落盘）。
2. **"同一个量在两个不同阶段读"极其容易被误读成噪声**：`g_diagAncUsed` 在 `OnGameTick`
   （帧内早）赋值、探针在 `ApplyPoseTarget`（帧末）读取 —— 这个"帧内两个阶段"本身就是根因的
   镜像，当时却差点被当成测量误差。**先确认两处读的是不是同一时刻的状态，再谈数值差异。**


## 10. 隐藏游戏 UI（面板复选框，v0.3.8 / 模块 1.0.0ak）

机制与实现见 `docs\10_隐藏游戏UI_探测与实施方案.md`；这里只列现象与处理。

### 10.1 勾了复选框但 HUD 还在

| 可能原因 | 怎么确认 | 处理 |
| --- | --- | --- |
| 没在发送数据（未武装/已停止） | `game_mod\EndfieldCamLink.log` 里有没有 `[ui] 隐藏游戏 UI:` 那一行 | 先武装/点开始发送 —— 勾选状态是**随数据包**送到模块的 |

| 两台通道都无效 | 日志有 `[ui] 隐藏 UI: … -> !! 没藏住` | 把这段日志发出来 —— 说明游戏的 UI 相机/接口变了 |
| **世界空间的东西还在**（怪物血条/状态条/头顶名字等） | 日志里 `[ui] 隐藏游戏 UI: …` 正常，但画面上血条还在 | 见 §10.5 |

### 10.2 HUD 隐藏着，按 ESC 之后又回来了（体力条/状态条忽然出现）

这是**默认"尊重游戏"策略**下的正常现象（2026-09-14 用户明确要求保留 ESC 界面可见，故默认如此）：
游戏在 UI 状态变化时会重建它自己的
`uiCameraCullingMaskConfigs` 配置栈（我们那条 `ECLHideUI` 被冲掉），而"尊重游戏"策略会选择**放行**，
于是整块 HUD（含**体力条**）一起回来。

日志里能看到：
```
[ui] 放行(尊重游戏): 游戏把遮罩改成 0x00000420(常规值 0x00000020 之外还多了 0x00000400) -> 界面交回游戏显示...
[ui] 重申隐藏: 遮罩回到 0x00000020 -> 已压回 0(第 1 次)
```

处理：`tools\send_cmd2.ps1 -Id 66 -A0 1` 切"严格保持"（或 ini `ui_hide_strict=true`）—— 这样战斗里
游戏频繁加层也不会让 HUD 回来，代价是 ESC 菜单也看不见。

> **2026-09-15 追加（1.0.0ar）**：严格保持下按 ESC 曾经是**全黑屏**。根因不是"世界没渲染"，
> 而是**遮罩=0 的相机照样清屏** —— ESC 界面态下 `UICamera`（深度 2，排在主相机之后）每帧把主相机
> 画好的世界擦掉。修法：隐藏时把 UI 相机整体 `enabled=false`（ini `ui_hide_disable_uicam=true`，
> 默认已开）+ 用主相机保活（`ui_hide_world_keepalive=true`，指令 73）把游戏写下的 `0` 按回去。
> 现在按 ESC 会看到**时停的世界画面、且画面里没有 UI**。完整证据链见
> `docs\10_隐藏游戏UI_探测与实施方案.md` §6。

### 10.5 怪物血条 / 头顶状态条藏不掉（世界空间 UI）

> **2026-09-15 已解决**: 实测确认它们在 **层 16 = WorldUI**（由 MainCamera 渲染），
> 默认已打开 `ui_hide_maincam_clear_bits=65536` —— 正常情况下不会再遇到本节的问题。
> 若仍然可见（例如 ini 被改回 0），按下面的步骤定位。

**原因**：屏幕 HUD 由只渲染**层 5** 的 `UICamera` 画，压它就能藏；但怪物血条/状态条这类
**世界空间**的东西由 `MainCamera` 渲染 —— 压 UI 相机管不到它们，这是设计使然，不是故障。

**定位**（只读，先跑这条）：

```powershell
tools\send_cmd2.ps1 -Id 70          # 图层名表 + 两个相机的遮罩(逐位带名字) + 未渲染的位
```

日志会给出 `位 13 = xxx` 这样的**图层名字表**；从名字就能大致判断哪层是"世界 UI"
（例如出现 `WorldUI`/`EnemyUI`/`HUD` 之类）。然后**一次性试**（3 秒后自动还原）：

```powershell
tools\send_cmd2.ps1 -Id 71 -A0 8192 -A1 3     # 8192 = 位 13; 换成你要试的层
# 同一时间只能试一组位掩码; 试几层就几个 2 的幂相加, 例如位 13+10 = 8192+1024 = 9216
```

看一眼画面：血条消失且**世界没缺东西** → 记下这个位掩码。
确认后设为**持续**（勾选隐藏 UI 时一并生效，取消勾选立刻恢复）：

```powershell
tools\send_cmd2.ps1 -Id 71 -A0 8192           # 不带 -A1 = 持续
tools\send_cmd2.ps1 -Id 71 -A0 0              # 撤销, 主相机立刻恢复
```

想每天开机就带着，把掩码写进 `game_mod\EndfieldCamLink.ini`：

```ini
ui_hide_maincam_clear_bits=8192      ; 十进制或 0x2000 都行
```

**安全说明**：这条路径**只动渲染遮罩**，且优先走游戏自己的配置栈
（`AddMainCamCullingMaskConfig` + `_UpdateMainCamCullingMask`，还原时 `Remove…` 让游戏自己重算）；
一次性测试有**到期自动还原**（每帧 tick 驱动，与是否武装无关），取消勾选/停发也会恢复。
如果清错了层导致世界缺东西，发 `-Id 71 -A0 0` 立刻回来，或直接取消勾选。

### 10.3 拍摄中 HUD 突然又出现（战斗中）

同上：游戏为某个 HUD 元素加了新图层（遮罩挡出现新位），默认策略会放行。
日志里 `[ui] 放行(尊重游戏): …` 那一行会写明**多出来的是哪一位**（例如 `0x00000400`）——
把这行发出来，就能判断它是"菜单/界面"还是"战斗 HUD 元素"。
只想让它一直藏着就切严格模式：`-Id 66 -A0 1`。

### 10.4 取消勾选后 HUD 没回来

模块在取消勾选时会 `RemoveUICamCullingMaskConfig("ECLHideUI")` 让游戏自己重算，
若结果仍是 0 会**补一次直接写回常规遮罩**（双保险），日志里是
`[ui] 显示游戏 UI: … -> OK`。若日志显示 `!! 仍为 0`，或压根没有这一行（数据流断了导致
帧末钩子没跑），手动兜底：

```
tools\send_cmd2.ps1 -Id 65 -A0 0      # 立即还原(一次性探测通道的还原)
```

最后手段：切一次场景/进出拍照模式（游戏会重配 UI 相机遮罩），或重启游戏。


## 11. 预设面板只剩一行红字（"预设面板出错: ..."）

### 现象

「运镜预设」分组里没有下拉栏 / 参数 / 按钮，只有一行
`预设面板出错: <异常类型>: <摘要>`。

### 原理（为什么"整个区域都没了"）

预设区整段被一个 catch-all 包着（`__init__.py` 的 `draw()` 里），目的是"预设出问题不能把整个
面板拖垮"。代价是：**区块里任何一句抛异常，它后面的绘制就全被跳过** —— 所以看起来像"整个预设面板
坏了"，其实只是某一行出错。

v0.3.9 起，出错时会同时把**完整 traceback**追加到预设日志：

```
%TEMP%\EndfieldCameraLink_preset.log
```

先看这个文件，再对照下表。

### 已经踩过/已修掉的两个具体成因

| 报错 | 根因 | 状态 |
| --- | --- | --- |
| `UILayout.label(): ... enum "UNDO" not found` | 预设区最后一行写的是 `icon='UNDO'`，而 **Blender 5.x 的图标枚举里没有 `UNDO`**（老版本有）。换成 `LOOP_BACK` 即修好 | **v0.3.9 已修**；并加了启动自检 `_check_icon_names()`：用 AST 扫插件里所有真实调用中的 `icon='...'`，与本版本 Blender 的图标枚举核对，发现非法名就写进上面那个日志 |
| 某个预设声明了 **5 个以上参数** | 面板只注册了 `ef_bridge_p0..p3` 四个属性，老代码会去取 `ef_bridge_p4` → `AttributeError` | **v0.3.9 已修**：只暴露前 4 个并提示"其余用默认值" |
| 预设头里的 `seconds` 写成非数字 | 面板为显示"默认秒数"直接 `float()` 它 → `ValueError` | **v0.3.9 已修**：解析失败就按 8.0 显示 |
| 换预设目录的瞬间下标越界 | 缓存与目录不同步时 `presets[index]` → `IndexError` | **v0.3.9 已修**：取值前再夹一次下标 |

### 自己排的话

```powershell
Get-Content "$env:TEMP\EndfieldCameraLink_preset.log" -Tail 40      # 完整 traceback
# 图标名自检结果(有问题才会有内容):
Select-String -Path "$env:TEMP\EndfieldCameraLink_preset.log" -Pattern '图标名自检' -Context 0,10
```


## 12. 怀疑"源码/产物被人改坏了"时怎么取证（多人/多 agent 协作）

**先记住一条**：本项目用 MinGW-w64 `g++ -shared -static` 构建的产物**不可复现** ——
同一份源码连编两次，文件长度完全相同（3173000 字节），但逐字节差约 **6500 处**。
所以：

> **不要用文件哈希判断"源码有没有被改坏"。** 每次构建的哈希都不一样。

差异**全部**落在 `.rdata` / `.data` / 几个 `.debug` 小节，**`.text`（代码段）差异恒为 0**。
因此正确做法是**按 PE 节区比对**：

```powershell
python source\tools\diff_dll_sections.py A.dll B.dll
```

判据：

| 观察 | 结论 |
| --- | --- |
| `.text` 差异 = **0**，各节区差异量与"同源码两次构建"的基线一致 | 两份产物**在代码与常量上等价** → 源码没有被改动 |
| `.text` 出现差异（哪怕几百字节） | 源码或编译选项确实变了 → 逐文件核对 |
| 文件长度不同 | 一定变了（改一行注释都可能改变长度） |

基线参考值（1.0.0ak 时期，A=成品、B=同源码重建）：
`.data 284 / .rdata 5764 / /14 10 / /29 200 / /55 18 / /67 56 / /107 144 / /123 36`，合计 ≈ 6521。

### 怎么找"别人动过什么"

```powershell
# 1) 最近被改动的文件(按时间排序, 排除构建/缓存目录)
Get-ChildItem D:\EndfieldCameraLink -Recurse -File |
  Where-Object { $_.LastWriteTime -gt (Get-Date).AddHours(-6) -and
                 $_.FullName -notmatch '\\build_ui\\|\\obj\\|__pycache__\\|\\backup\\' } |
  Sort-Object LastWriteTime | Select-Object LastWriteTime, Length, FullName

# 2) 新增/残留文件(备份、临时、副本)
Get-ChildItem D:\EndfieldCameraLink -Recurse -File |
  Where-Object { $_.Name -match '\.(bak|orig|tmp|rej|save|old)$|~\$|\(2\)' }

# 3) 源码里有没有不属于它的痕迹(按关键字)
Select-String -Path D:\EndfieldCameraLink\source\src\*.cpp -Pattern '\[scan\]|field_flags|static_data'
```

### 运行时证据（最硬的）

* `game_mod\EndfieldCamLink.log`：**每次注入都会重写**，所以文件里的行属于"那一局加载的模块"。
  看到不认识的日志前缀（例如 `[scan]`）就说明那一局跑的不是当前源码构建的模块：
  那局的日志要单独看，别当成当前模块的行为。
* `%USERPROFILE%\AppData\LocalLow\Hypergryph\Endfield\Player.log`：崩溃栈里会写模块名与函数
  （`(EndfieldCamLink) ecl::函数名`）以及模块的 `SizeOfImage`。
  **`SizeOfImage` 可以直接区分是哪一次构建**（本项目 1.0.0ak = 1753088；
  2026-09-14 那局崩溃的模块是 1777664，属于另一份构建）。
* `%TEMP%\Hypergryph\Endfield\Crashes\Crash_*\crash.dmp`：完整转储。

> 实例见 `VERSION.txt` 的「完整性与事故核查 (2026-09-14)」一节：
> 有一次外部改动构建的模块在游戏里崩溃（崩溃栈里是 `ecl::GameSysUiSceneAudit`，本项目**没有**这个
> 函数），回滚后按上面的方法核对：`.text` 差异 0、节区差异量与基线逐项一致、全项目搜不到对方痕迹。

> **1.0.0aq 补充（很重要）**：自动回退最初只覆盖了"显式来源 1..4"，而**面板/ini 默认用的是来源 0
> （武装点 = 扫描模式）** —— 于是那条路径完全不生效（实测日志里"自动回退"0 行），
> 而且扫描模式的逐帧兜底会**再次接受粘性缓存值**，把旧位置捡回来。
> 1.0.0aq 起：来源 0 也会走自动回退（每帧 + 冻结锚点两处都覆盖），且自动回退开着时
> **兜底扫描只认实时可读的候选**，全都不新鲜才用引擎相机（日志 `[anchor] 自动回退生效: …`）。
> 如果你在某个界面发现相机没跟过去，先看日志里有没有这几行 —— 有行说明逻辑跑了，没行说明这一段没被覆盖。
