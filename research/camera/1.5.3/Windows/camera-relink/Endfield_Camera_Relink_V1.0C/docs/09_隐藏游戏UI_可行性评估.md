# 隐藏游戏 UI · 可行性评估

> 需求：在 Blender 插件的侧栏面板里加一个（或一组）按钮，用来**隐藏终末地的游戏 UI**（HUD），
> 以便用本链路拍出干净画面。
> 本文只做评估，不含实现。结论与依据都尽量落到"包内已有的实测证据"上，凭猜测的地方明确标注为待验证。

---

## 〇、结论

| 问题 | 回答 |
|---|---|
| 属不属于复杂功能？ | **不属于。** 属于**小功能**，量级接近已完成的「锚点微调（cmd 48）」「重新冻结锚点（cmd 49）」 |
| 估算工作量 | **1.5–2 天**（其中**半天必须先做一轮只读探测**）；若不命中原生开关、退到渲染层兜底，再 +1 天 |
| 难在哪 | **不在工程量，在"机制识别"** —— "到底哪个开关控制 HUD"目前只有间接线索，没有实测证据 |
| 最大技术约束 | 本作 **`FindObjectsOfType` 不可用且危险**（返回 null / 抛异常 / 每帧枚举会把内存吃光导致引擎崩溃，v8 已删掉这条路）→ 直觉上最省事的"遍历 Canvas 逐个 `SetActive(false)`"**不能做** |
| 能否回退 | 能，而且很干净：开关放进共享内存 flag 位，**停止发送 / 数据流中断 >500 ms 时自动还原**（现有安全阀直接复用） |

对照：本工程里真正算"复杂"的是**定镜头/随角色双链路**、**锚点冻结**、**偏移驱动**那几轮 —— 它们难在
坐标系统一、写入-测量标定、抗抖动、跨模式状态机。而"藏 UI"是**单一布尔开关、无坐标、无标定、无插值**。

## 一、藏 UI 的四条可能通道

包内符号清单（`docs\reference\inventory_camera_symbols.log`，运行时从 `Gameplay.Beyond.dll` 枚举，
8000 行上限）里能找到的全部相关线索如下。**注意：符号名只是线索，不等于"这个开关真的管 HUD"。**

| # | 通道 | 包内证据 | 实现难度 | 主要风险 | 评价 |
|---|---|---|---|---|---|
| **A** | **游戏自身的 HUD 开关**（首选） | `CameraControllerBase._hideHUD` 字段 + `get_hideHUD()`；`CameraManager.m_needHideHUD` 字段 + `_UpdateHUD()` + `_CurrCameraNeedHideHUD()` | 低 | 字段语义未实测；若 `_UpdateHUD` 每帧重算，写错层会被覆盖 | 若成立 = **最干净**：让游戏自己的逻辑去显隐，退出/切相机时游戏自己还原 |
| **B** | **UI 相机渲染层**（兜底） | `CameraManager.get_uiCamera/set_uiCamera`、`GetUICamDefaultCullingMask()`、`_SetUICameraCullingMask(int)`、`GetUIModelLayerMask(1)`、`EnableUIModelCullingMask(3)` | 低 | ① 若 HUD 是 `ScreenSpaceOverlay`，**关相机根本不管用**（Overlay 不经过相机）；② 全关会连"UI 里的 3D 模型层"一起关掉（所以要保留 UI 模型 layer） | 可行，但需要先确认 Canvas 的 renderMode |
| **C** | **UI 节点层**（疑似游戏原生做法） | `UiNodeSnapshot`：`activeSelf / activeInHierarchy / canvasGroupAlpha / canvasGroupInteractable / graphicEnabled / graphicColor …` | 中 | 找不到"谁在调用它/它的持有者是谁"就无从下手；而按类型找实例的路被 §三.5 封死 | 信息量最大的一条线索：**游戏自己就是"快照 → 藏 → 还原"这套做法** |
| **D** | 第三方 MOD 思路 | 社区存在专门的「隐藏 UI 与 UID」MOD | — | 与本包链路无关（不进游戏渲染之外的东西），且涉及 UID 水印 | 只当"需求真实存在"的旁证，不作为实现路径 |

> 社区侧佐证：官方拍照模式是"拍片工作流"，社区另有专门教程讲怎么藏 UI 拍干净截图
> （[Ultimate Gacha 教程](https://ultimategacha.com/arknights-endfield-how-to-hide-ui-clean-screenshots-content-creation/)、
> [拍照模式说明](https://gamerant.com/arknights-endfield-how-use-photo-mode-camera/)），
> 同时也有第三方 [隐藏 UI 与 UID MOD](https://m.18183.com/xiazai/bd_21051.html) ——
> 说明**游戏没有"随时可用的一键隐藏"**，这件事确实需要额外手段。

### 一个合理的当前假设（待实测，不要当结论）

本链路用的是**官方自由相机**（`OpenMarketingCamera`，激活控制器是 `MarketingCameraController`），
而游戏自己的拍照模式用的是**快照相机**（`SnapshotCameraController`）。
符号层面看，HUD 显隐是**跟随"当前激活的相机控制器"的 `hideHUD` 描述位**的
（`CameraManager._UpdateHUD()` 读 `_CurrCameraNeedHideHUD()`，后者源自 `CameraControllerBase._hideHUD`）。

**如果**自由相机的 `_hideHUD` 是 false、而快照相机是 true，那么"武装后 UI 还在"就有了物理解释，
而"藏 UI"就退化成：**把当前控制器的 `_hideHUD` 置 true，让游戏自己去 `_UpdateHUD()`**。
这条假设只要一轮探测就能证实/证伪 —— 这正是下面建议先做探测的原因。

## 二、为什么判定"不复杂"：需要的东西包内已经都有

| 需要的能力 | 包内现状 |
|---|---|
| 拿到 `CameraManager` 实例 | 已有 `CameraManagerInstance()`（走静态 `CameraUtils.get_cameraManager`） |
| 拿到当前激活的相机控制器 | 已有 `get_curActiveController` 的使用经验（`docs\04` 已记录其返回 `MarketingCameraController`） |
| 读写托管字段 | 已有 `class_get_field_from_name` / `field_get_value` / `field_set_value` / `field_get_offset`，且**带值类型尺寸校验**（上次崩溃的教训已固化进 API 层） |
| 调用任意托管方法（含私有） | 已有 `InvokeLogged` / `CallGetter`，且带签名体检（cmd 30/44）与参数类型校验 |
| 枚举类成员找符号 | 已有 cmd 26 + `inventory.cpp`（本文件的全部符号线索都出自这套） |
| 写入-测量标定 | 已有 cmd 45/46 那一套方法（先只读、再小步写、每步稳定帧数） |
| 面板加按钮 | 插件现有 9 个操作符 / 5 个面板分组，加一个勾选框是同一量级的工作 |
| 状态通道 | 共享内存包 flag **bit 6 空闲**（bit 0–5 已用）→ **不需要改包长/版本号，老插件不置位即行为不变** |
| 自动兜底 | 现有"数据流中断 >500 ms 停止位姿写入"的安全阀可直接挂上"还原 UI" |

所以真正要新写的只有四件小事：

1. **1 个只读探测指令**（如 cmd 50「UI 体检」，打印 §六 列的那几项）；
2. **1 个开关指令**（如 cmd 51，置/清当前控制器的 `hideHUD`，并记录原值）；
3. **1 个 flag 位**（bit 6 = `kFlagHideUi`）+ 关闭/断流时还原；
4. **面板一个勾选框** + 自检里 4–6 条断言（面板当前状态的只读回显也要有）。

## 三、真正的难点（5 条，都不是"写多少代码"的问题）

1. **机制识别（唯一的不确定项）**
   `_hideHUD` / `m_needHideHUD` / `_UpdateHUD` 三个符号都存在，但**谁管用、当前值是多少、拍照模式下会不会自己变**，
   没有实测证据。这一项决定了是"半天搞定"还是"要换通道"。

2. **别写到会被覆盖的那一层**
   `m_needHideHUD` 很可能是**每帧由 `_UpdateHUD()` 重算的结果**，直接写它下一帧就被覆盖。
   应该改**源头**（当前控制器实例的 `_hideHUD` 描述位），让游戏的逻辑自己算出结果。
   —— 这正是本工程已经踩过两次的坑（"面板 draw 里写属性被 Blender 回滚"、"写枚举触发 update 覆盖"）。

3. **还原必须自动，而不是靠人记得点回去**
   必须记录**原值**并在三种时机还原：插件取消勾选、停止实时发送、数据流中断 >500 ms。
   放进 flag 位就是为了复用现有安全阀 —— 这是本方案能"零残留"的关键。

4. **游戏自己也会动 UI**
   `UiNodeSnapshot` 这种结构的存在说明游戏在进出拍照模式/切场景时会**快照并还原** UI 状态。
   影响：我们的开关可能被游戏覆盖（其实等于自动兜底，是好事），但**面板上显示的按钮状态可能与实际画面不一致**
   → 面板需要一个"查询当前实际状态"的只读回显，而不是只显示用户点的值。

5. **不能做场景遍历（硬约束）**
   `FindObjectsOfType` 在本作不可用，且一旦放进每帧数据流会导致提交内存耗尽、引擎崩溃（v8 血泪教训）。
   因此"找 HUD 根节点 → `SetActive(false)`"这条最直觉的路，**只能**通过"某个管理器/静态 getter 给出的实例引用"来做，
   不能靠搜索。评估 §一 里把通道 C 排在中位、而且必须先做探测，原因就在这里。

## 四、风险与副作用（要一起决定，不能只看"能不能做"）

| 风险 | 级别 | 说明 / 缓解 |
|---|---|---|
| 藏掉 HUD 后看不到交互反馈 | 中 | **建议限定在"已武装 + 拍照模式"下生效**，正常游玩时不提供该开关；退出拍照模式自动还原 |
| 可能连"退出拍照模式"的按钮一起藏掉 | 中 | 需要文档写清键盘退出方式；控制台 `[4] 关闭相机控制` 与 >500 ms 断流都会还原 |
| **UID / 水印** | **高（合规）** | 社区那类 MOD 是"隐藏 UI **与 UID**"。本功能应**明确只藏 HUD，不碰账号 UID 水印** —— 隐藏账号标识属于另一类性质，超出"只改显示"的边界，也与 `docs\05` 的性质说明不一致 |
| 每帧强制会掉帧/涨内存 | 低 | 本方案只在**状态切换时写一次字段**，不新增每帧遍历（与历史崩溃路径相反） |
| 游戏更新后符号失效 | 中 | 与现有全部功能同一风险等级；包内已有 dump 流程，重跑一次即可 |
| 与运镜/双模式的相互作用 | 低 | 开关是正交的布尔量，不改位姿、不改 FOV、不动景深；出图构图不受影响 |

**成功判据（三条硬指标）**：
① 勾选后 HUD 消失，且**画面构图/FOV/景深一律不变**；
② 取消勾选、停止发送、或插件崩溃断流后，HUD **自动回来**；
③ 反复开关 20 次不崩、内存无增长（沿用既有压力测试方法）。

## 六、建议的落地顺序

1. **先只做探测（本轮不建议直接写开关）**。这是一次**纯只读**操作，风险为零，但能把唯一的不确定项消掉：
   - `CameraControllerBase.get_hideHUD()` 的实际返回值（当前激活控制器）
   - 该实例的 `_hideHUD` 字段原始值
   - `CameraManager.m_needHideHUD`（看它是否等于上面的值 → 判断"谁覆盖谁"）
   - `uiCamera` 的 `cullingMask` / `GetUICamDefaultCullingMask()` / `GetUIModelLayerMask(1)`
   - 拍照模式开关前后的上述值差异
2. 拿到读数后，**按事实**选通道 A 或 B，再实现 cmd 51 + flag bit 6 + 面板勾选框。
3. 按 §四 的三条硬指标验证，然后补文档、重打包分发。

> 如果测出来是通道 A（大概率），这个功能的实现就会非常短：**一次字段写 + 一次还原**，
> 连 UI 层级都不用碰 —— 也就不会出现"藏一半、留一半"这类难缠问题。

## 七、结论

- **复杂度：低–中（小功能）**，不是复杂功能。基础设施（实例获取、字段读写、方法调用、符号枚举、面板、验证脚本、状态通道）全部已就位，工程量约 1.5–2 天。
- **不确定性只有一个**：哪个开关真正管 HUD。**用半天做一次只读探测就能消掉**，不值得靠猜。
- **必须先划清的边界**：只藏 HUD，**不碰账号 UID/水印**；只在拍摄（已武装 + 拍照模式）状态下允许，并且取消/停止/断流时**自动还原**。
- **建议**：先批准"探测轮"这一小步（无副作用、可随时丢弃），拿到实测读数再决定是否进入实现轮。
