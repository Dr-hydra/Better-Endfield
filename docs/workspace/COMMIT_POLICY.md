# 提交署名规范

2026-10-30：本仓库曾因一次合并把外部贡献者和 AI 工具的身份带进 `main` 的历史，事后重写了 `3c3bd3bd..HEAD` 的九条提交。本文固定当时的判定依据，避免再犯。

## 作者与提交者

- 进入 `main` 的提交，作者和提交者都是维护者 `Dr-hydra <Dr-hydra@users.noreply.github.com>`。历史里的 `116339679+Dr-hydra@...` 是同一人的旧邮箱，视为等同。
- 不使用第二个身份提交。AI 工具可以参与实现、审阅和验证，但不作为作者或提交者出现，这一条与工具是否参与了工作无关。

## 提交信息

- 不得包含工具署名或会话标识，包括 `Co-Authored-By: Claude`、`Co-authored-by: Claude`、`Claude-Session:`、`Generated by ...` 等。工具的实际贡献写在正文的功能与验证说明里，不写进元数据。
- 摘要用 `type(scope): 说明`，`type` 取 `feat`、`fix`、`docs`、`chore`、`refactor`、`test`、`build`、`release`、`merge`。正文说明动机、影响范围、验证方式和未覆盖部分。
- 合并提交的正文写清来源分支和议题号，例如 `merge: try zhuran24 jsspsi_quality (issue #32)`。

## 外部贡献

- 贡献者的署名出现在代码注释、模块文档、发布记录和议题链接里，不由提交作者体现。现行例子见[连续冲刺实现说明](../actions/SPECIAL_DASH_CONTINUOUS_ANIMATION.md)与 4.1.1 发布记录。
- 外部 fork 的提交对象不进 `main`：先 `cherry-pick` 到本地分支，按需 `squash`，再以维护者身份提交。直接 `git merge` 外部分支正是把整段外部历史并入 `main` 的原因，不要这样做。
- 致谢和来源记录不随重写丢失；重写只改身份与署名尾巴，不改代码、文档内容和提交正文的事实描述。

## 发布记录里的提交号

- `docs/workspace/releases/<软件版本>/` 记录的短 SHA 必须指向 `main` 上真实存在的提交。改写历史后同一轮内同步更新，不留悬空引用。
- 记录写短 SHA（8 位）即可；不要用会随重写失效的早前版本号冒充当前提交。

## 落地检查

- 启用钩子：`git config core.hooksPath .githooks`。`.githooks/commit-msg` 会拒绝带工具署名或非维护者身份的提交。
- 本机工作区和 AI 会话目录（`.workbuddy/`、`.workbuddy-ai/`）必须在 `.gitignore` 里，任何一次 `git add -A` 都不应把它们带进提交。
- 推送前用 `git log --format='%ae' -20 | sort -u` 自查，出现维护者以外的邮箱就停下来。
