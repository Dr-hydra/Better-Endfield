# BEM 第一版数据结构讨论稿

状态：2026-09-18 草案，尚未冻结、尚未实现。现有读取器仍只读取 BEMPC24/BEMPC25。
本文中的 BEM 1.0 是新正式协议，不是把旧文件的 version 字段改成 1。

## 已确认的设计方向（2026-09-18）

- 一个包对应一个角色，可以包含多种固定外观；第一版由管理 UI 选择，同一时刻启用一种，
  下次启动游戏生效。游戏内切换留待后续实现，不作为第一版承诺。
- 每个外观有稳定 appearance_id、名称、说明、可选预览图及完整部件配置；包指定
  default_appearance_id。选择保存在用户配置，更新后所选 ID 消失时提示并回退到默认外观。
- 外观通过 ID 共享 Mesh、骨骼表、材质与纹理数据，不采用外观间继承/叠加补丁。
- 数据资源独立压缩，支持 raw 和 Zstd，默认写入等级 9；压缩后不节省空间则存 raw。
  资源目录记录 codec、offset、stored_size、decoded_size；按所选外观读取和解压依赖。
  压缩等级属于打包选项，解码协议只要求对应 codec。
- 共享 payload 去重，不降低几何精度或纹理分辨率。压缩减少磁盘体积，不承诺降低 GPU 驻留内存。

洁尔佩塔 Outfit B 测量：原包 480,065,480 字节，7 条纹理记录只有 3 份独立 payload，
去重未压缩估计 211,630,024 字节。直接整体 Zstd 9 为 82,234,310 字节；
元数据/几何组合块及三份独立纹理分别 Zstd 9 后合计 36,016,253 字节，约 36.0 MB。
等级 3/15 分别为 38,150,859 / 35,696,472 字节。全部压缩结果已解压逐字节核对。
这是单套 Outfit B 的测量估计，不是已生成的正式 BEM 1.0 包；正式分块粒度、目录、
预览图与新增外观会改变最终体积。记录：`artifacts/native-parser/gilberta-compression-estimate.json`。

## 第一版范围

以已验证的能力为边界：静态外观、几何替换/保留/隐藏、骨架与材质来源分离、
合并骨骼 palette、按绘制段选取原生材质、纹理替换、UInt16/UInt32 几何索引。
运行时接受 BEM；EFMI 等源格式只由离线工具处理。Android 支持尚未实现。
不新增任意 Shader、脚本、热键换装、形态键、自动分片或自定义多级 LOD。
LOD 锁定继续属于运行时配置：有启用的 Mod 强制开启，否则使用独立开关。

## 当前协议需要厘清的问题

- 包外 `runtime.ini` 承担角色/资源/原 Mesh 身份；单独一个包缺少完整安装信息。
- v25 用旧 reserved 字段装 palette/draw 数量，依赖固定顺序串行读取。
- 三条顶点流依赖目标原 Mesh 声明，包内只有声明 CRC，不能独立解释全部通道。
- 骨骼来源、材质来源绑定目标组件/槽位及名称 CRC；跨平台资源不能直接假定一致。
- 纹理记录同时承载 payload 和绑定，多个名称 pin 会复制相同纹理字节。
- 64 个组件与 32 位纹理绑定掩码的表达范围不一致，不宜成为正式协议设计。
- “支持 16 位输入骨骼索引”不等于“输出 16 位骨骼通道”：现有输出为局部 UINT8
  palette 索引，v25 每组件最多 256 个 palette 项。正式文档必须区分输入和输出。

## 建议的逻辑结构

下表是待讨论的逻辑模型，不是可据此写二进制的已发布规范。

| 数据块 | 建议字段及职责 |
| --- | --- |
| Header / SectionDirectory | 独立 magic、major/minor、header_size、file_size；段类型、段版本、required 标记、offset/size/count |
| PackageInfo | 稳定 package_id、显示名、作者、包版本、目标角色、所需运行时能力 |
| Appearance | appearance_id、名称、说明、可选预览、完整部件配置引用、额外能力要求；包指定默认外观 |
| TargetProfile | profile_id/revision、目标平台与资源快照标识；world/UI 根和组件身份；原 Mesh、索引数、原生声明、骨骼/材质来源契约 |
| Component | component_id、目标组件引用、操作 replace/keep/hide、mesh 引用；不以零长度网格隐含隐藏语义 |
| Mesh | 顶点数、完整属性声明、流 stride/payload 引用、索引类型/数量/payload 引用、bounds、skin 引用 |
| Skin | 权重/索引声明、局部 palette；各 palette 项引用 donor 组件、骨骼槽位和可核对名称；保留 bindpose/空间一致性检查 |
| Draw | Mesh 内 start/count，独立的 donor 材质引用和纹理绑定列表；有序覆盖 IB，重复材质槽仍可明确表达 |
| Texture / Binding | 尺寸、mip、格式、色彩空间、payload 引用；绑定另记目标材质属性名/原纹理身份和替换 texture_id |
| Payload | 顶点、索引、纹理和预览等数据；可共享引用；codec、offset、stored_size、decoded_size，独立 raw/Zstd 块 |

PackageInfo 的角色名用于展示，真正兼容性由 TargetProfile 和运行时观测共同决定。
建议包携带使用到的 profile 契约子集，不内置所有角色资料；完整资料库留在工具侧。
安装启用状态、多个包的选择和独立 LOD 偏好留在用户配置，不写进作者包。

## 二进制约定建议

- 固定小端、UTF-8、定宽整数；不落盘 C++ 指针、容器布局或 Unity 对象地址。
- 文件/段偏移与长度用 uint64；局部 ID 与计数用 uint32；具体对齐和字段偏移待冻结。
- 显式写出顶点 semantic、format、dimension、stream、offset 和 stride。
  第一版只接受已有运行时能够处理的布局；“自描述”不代表支持任意属性组合。
- 几何索引保留 UInt16/UInt32；蒙皮输出先保持现有 UINT8 局部索引能力。
  16 位输入可离线重映射；超过 palette 容量拒绝，不截断也不自动分片。
- 第一版使用共享 payload 和独立 raw/Zstd 压缩块，不采用必须整体解压的单一压缩流。
  解码前检查声明的解压长度和资源预算，解码后核对实际长度；完整容器字节布局仍待冻结。
- 已有 CRC 可作为快速比较辅助，正式身份保留字符串/明确字段，不把 CRC 当安全校验或唯一身份。
  本草案不要求计算产物哈希。

## 兼容性与失败行为

- PC 和 Android 可以使用同一协议，但同一个具体包能否通用取决于 profile、布局、骨骼、
  材质和设备能力是否都匹配。Android 不能继承 PC 实机通过标记。
- world/UI 分别建立资源路由并核对契约；离线证据确认共享 Mesh、骨骼映射和材质时，
  可复用一侧运行时观测，并标注证据来源。存在差异或加载校验不符时补采对应侧，不能静默猜测。
- 不把 Windows native Mesh 偏移、GPU 地址、托管字段偏移或渲染器 property ID 写成跨平台契约。
- 未知 major、未知 required 段或缺失必需能力拒绝；可选段按长度跳过。
  minor 只做兼容扩展，已定义字段不得改变语义。
- 校验长度溢出/越界、段重叠、重复 ID、悬空引用、索引范围、draw 分区、骨骼/材质来源，
  创建前核对所需图形能力。按现有事务交付原则，构建失败保留或恢复原绑定。
- 解析成功、目标匹配、实机外观通过分开记录；代码中的容量上限不等于手机性能承诺。

## 角色资料分发建议（待讨论）

角色原生资料与具体 Mod 的转换配方分开维护：前者可跨作者复用，后者描述某个源包
的入口、draw、骨骼映射、贴图语义与外观状态，不是通用角色资料。

| 层次 | 内容 | 建议发布位置 |
| --- | --- | --- |
| 采样原始证据 | 离线数据库、Bundle/PathID 引用、原生贴图字节、运行时观测、诊断记录 | 项目研究资料；不要求每个玩家下载 |
| 创作者角色 profile | 资源/组件身份、完整顶点声明、骨骼顺序/路径及 bindpose、材质槽/纹理属性、world/UI 差异、平台/版本与验证状态 | 随创作工具发布或按角色下载，不必绑定主程序版本 |
| 包内适配子集 | 导出实际使用的目标资源、组件、声明、骨骼与材质来源及兼容条件，profile_id/revision | 随 BEM 包发布；含只作 donor 的未替换组件依赖 |
| 运行时引擎适配 | IL2CPP/Hook、原生 Mesh 布局解析、平台 ABI、图形能力检查 | 随软件发布，不由作者包提供内存偏移或地址 |

同角色、平台和兼容资源版本的采样成果可复用，不应每制作一个 Mod 都重采样。
当前 finalize 工具仍要求 world/UI 运行时观测；游戏资源、平台、组件或声明发生相关变化时
更新/补齐对应资料。加载包时的轻量匹配校验继续保留，它不等于每次导入都跑完整采样。
创作者需要标准化 profile 和可读说明，无需自行理解原始 dump；新的 Mod 仍需明确自身
材质意图与骨骼来源，通用 profile 不能自动解释任意源 Shader。
