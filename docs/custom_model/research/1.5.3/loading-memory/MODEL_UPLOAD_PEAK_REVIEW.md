# 模型首次加载的瞬时 GPU 压力（2026-10-03）

本轮重点是用户描述的“有 4K 贴图的模型加载时增加约 2GB 或更多，加载完成后回落”，且该问题早于热切换。热切换旧资源释放另外处理，不用它解释本次首次加载峰值。开始检查时 ADB 无设备；随后用户提醒后确认无线连接，读取了 3.4.3 手机的现有日志和必要包元数据。游戏当前没有进程，本轮没有 GPU 驱动峰值实测，不能宣称已复现或定位了这 2GB 的唯一来源。

## 当前判断

最值得验证的是同步资源交付中的连续贴图上传及其暂存叠加，其次是实际新建 Texture 数量。代码已经明确存在这些路径；驱动在什么时候提交、回收 staging，仍需现场观测。不能把 BEM 解压的 CPU 副本节省量当成 GPU 峰值改善，也不能仅凭“4K”解释 2GB。

- `native/modules/custom_model/module.cpp` 的 `PrepareResource` 连续构建全部组件和材质；每张新纹理连续执行 Texture2D 构造、`LoadRawTextureData(IntPtr, size)`、`Apply(false, true)`，完成后才整体提交。这里没有按帧或上传字节数限流。上传请求集中在交付调用返回以前。
- `Apply(false, true)` 已放弃 Unity 的可读 CPU 贴图副本，且没有生成额外 mip。它不保证 GPU/驱动上传暂存此时已回收。增加 GC 或再调用 Apply 不构成显存降峰方案。
- 默认缓存仍按组件建立。启用已有 `loading_optimization` 后，在一次构建事务中按 `(BEM texture index, 原 Texture 对象)` 复用。不同 source Texture 或不同 BEM texture index 仍可能新建。仅仅 payload 共用，不能认定 GPU Texture 也共用。
- 安卓 UI-first 可复用已验证 donor；world-first 在普通模式下有确定的重复构建，见下节。UI donor 原资源自身的同步加载仍可能与这批上传处在同一交付窗口，需要实际时间线判断。
- 安卓目前默认原样导入；用户手动转换才选择 ASTC/RGBA32。运行时会先检查游戏 backend 的 `SupportsTextureFormat`，不支持即拒绝该构建，不能无证据声称成功加载路径必然把全部 BC 软件解码成 RGBA32。
- Mesh 的可读副本、decoded payload cache 和第一人称 CPU 几何缓存属于 CPU 侧。它们可能影响手机统一内存统计，但不是已测 GPU residency。
- 另一个需要与替换上传分开的加载放大点：`BemInstalledResources` 当前生成 `lod_pipeline=1;lod_npc=1`，除目标替换外，还修改 `NPCCrowdLODSetting` 的全局可见距离为 `(1000,1000)`、最大渲染数为 100，并关闭 camera physic cull。手机旧日志也确认这组参数被应用。这可能扩大同时加载/可见的原生 NPC 资源；本轮没有资源请求时间线，不能把其容量算进上述 BEM 字节表或认定它是 4K 触发的主因。保留该行为，后续可独立对照“只保留必要 pipeline bias”的加载压力，验证后再决定是否收缩全局 NPC 设置。

一张 4096² RGBA32 为 64MiB，完整 mip 链约 85.33MiB；BC7/ASTC 4×4 的单 mip 为 16MiB，ASTC 6×6 约 7.12MiB。即使尺寸一样，格式、mip、贴图数量、重复对象、暂存数量都会改变结果。用户观察到加载后回落，更适合以“同时在途的上传及原生资源加载”验证，不能据此排除其他分配或认定内存泄漏。

校园默认数据按组件引用约 196MiB，单靠已知的这份纹理容量不能证明 2GB 峰值；仍需确认用户现场转换后格式、实际新建数和上传暂存的叠加。此处没有把 PC 包尺寸当成手机当前已安装包的尺寸。

## 本轮增加的定位能力

生产 `ConstructionScope` 在实际产生新 Mesh/Texture 的事务结束时输出一条 `Model upload transaction`，包括：资源名、是否发布、Texture 构造数、成功 Apply 数、实际提交 texture payload 字节、最大单张字节、Mesh 提交数/字节和耗时。失败事务的已上传对象也计入；跨组件命中缓存不重复计数。UI 无新增说明或诊断入口。

这些是 API 请求量，不是驱动显存或 staging 测量。日志用于快速判定：一套 4K 纹理究竟提交了多少份、是否发生多个 UI/world 构建、回滚后是否又尝试。需要与系统 Graphics/GL、GPU profiler 的时间线一起看，不能直接把日志 bytes 称为峰值。

验证：生产材质测试覆盖优化开/关的实际构造和提交数、共享失败清理、原资源不被销毁；元数据工具用既有合成包核对 geometry/texture 字节及 hidden 选择无上传。双端生产编译由本轮汇总记录。

## 优化顺序

1. **先用上述计数核对重复构建。** 已有加载优化能减少跨组件同 source 的提交；如仍大量重复，进一步按当前纹理内容与完整 sampler 状态核实等价后复用，而不是删掉 source 身份条件。仅凭名字、尺寸或 payload ID 合并可能改变颜色或采样。
2. **GPU 上传按帧预算，是直接针对暂存峰值的方案。** 将解压/计划与 Unity 资源创建分离，在主线程分批创建和 Apply，限制每帧提交字节；资源完整、校验通过后整体发布。当前 `_FinishWithAsset` 同步交付不能在循环里直接 sleep/切线程/返回半成品。必须先确认可延迟完成的游戏资源入口和引用所有权，让游戏在等待期间继续渲染、消费上传并回收暂存；否则“分批”仍发生在同一阻塞调用中，没有 GPU 降峰收益。
3. **保留原分辨率时优先减少在途资源，降低分辨率作为另一选项。** 手机 ASTC 能减小资源和上传字节，但线性 4×4 和部分 BC7 的字节数相同，不能保证每张都显著省。可增加可选 2K 上限（所有输入格式都覆盖），通常减少约 3/4 像素容量，但会改变画质，不应偷偷启用。报告中的 2K 列只是方案估算，没有修改模型包或生产转换设置。
4. **UI donor 加载和替换上传错峰。** 如时间线确认它们同窗叠加，可将已验证 donor 获取/等待与后续上传调度拆开。需要保持 Android LOD/bone/material 校验和 world/UI 同一代次，不通过删除 donor 来降低峰值。

游戏原生资源交付可能具有异步上传或纹理流送能力，但本轮没有其上传时间线，不能把这个推测当成已证实的区别。下一次只需一个确定能复现的 4K 包，记录冷启动的原生加载与替换加载，并结合事务计数和 GPU 时间线；无需为了本项反复切包或研究热切换回收。

- Aglina：日志 324–382 为 world-first 构建，383–433 为随后 UI 构建。两批各 8 次 `built t=`，名称、尺寸、mip、色彩属性完全相同。读取手机实际已安装 ASTC 包元数据，按这些记录匹配 payload 尺寸：**每批 387,856,640 B（约 369.89MiB），两批共约 739.78MiB**。这是日志中成功新建/上传的 payload 量，不是测得的 GPU peak。该会话使用 8K，并非用户描述的每个 4K 包。
- 同份日志的提弗洛斯 4K 包也出现 world 提交后 UI 重新 `built t=`，包括三张 4096² 的 cloth_01 D/N/P（BC7、BC7、RGBA32）和大量较小纹理。说明重复路径并非只在 8K 或某个角色发生。
- 生产原因：`world_resource_adapter.inc` 先为 world 构建 UI sources，但仅在 `g_hot_switch_runtime` 开启时将其交还联合事务。普通模式随后 `ensure_ui()` 对尚未提交的 donor 又执行 `PrepareResource`。这是普通首次加载的重复路径，热切换开关只决定是否走已有的联合发布，并不意味着历史峰值由热切换引入。
- 修正沿用已有联合事务：只要调用者提供 paired 输出，普通模式也交还同一 sources，world/UI 共用这一批替换资产并一起提交、回滚、记录完成身份。cached donor 和未提供 paired 输出的验证调用保留原语义。此修正消除一轮确定的重复上传，不擅自降低分辨率或启用实验开关。

两批新 GPU 资源、原版 donor、CPU 可读存储及在途 staging 有机会同时存在；实际每项占用、时间重叠与驱动统计口径仍待 GPU 时间线确认。已有日志足以证明重复构建，**不足以把 2GB 都归因于它，或保证修复后峰值正好减半**。对剩余峰值的优先方案仍是上传节流/可延迟资源交付。

## 新构建的用户观察：单次约 0.9GB

用户澄清：每次打开 UI 会重新构建；**每一轮构建本身**瞬时增加约 0.9GB，结束后回落。不是把多次构建累计上传量称为一次 peak。当前值仍需优化，不能直接称为正常或已解决。

`device-current-peak-diagnostics.log` 的新统计：world 3438 行构造/Apply 各 8 次、387,856,640 B、Mesh 12,294,548 B，耗时 1356ms；紧接着的 `ensure_ui` 没有第二轮上传，联合发布已在这次日志中生效。后续两个 UI 事务分别在 3561、3619 行，同样各上传 387,856,640 B，耗时 1637ms、850ms。此处后续的重复是 UI 再交付/再构建，与首次 world 内的联合发布属于不同窗口。

这次日志的实际贴图是 **8K ASTC**，其中最大一张 67,108,864 B（64MiB），而非只有 4K。单轮约 369.89MiB 请求量可与新 GPU 资源、Unity CPU 可读/加载存储、驱动 staging 重叠；这些内存种类不能未经驱动测量都叫显存，更不能将三轮之和当单轮的 0.9GB。读取时游戏已退出，`dumpsys meminfo` 没有进程，未取得同窗口峰值时间线。

现有日志已使“实际一次上传多少”可核对；剩余重点是单次批量上传的在途峰值。UI 每次重建的复用、旧资产释放与缓存策略另记为后续项，不用它们替代本轮单次上传节流研究。
