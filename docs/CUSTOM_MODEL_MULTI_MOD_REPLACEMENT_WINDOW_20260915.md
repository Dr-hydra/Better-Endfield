# 多角色 Mod 的替换窗口调研与建议（2026-09-15）

状态：已增加双角色双路径实验代码，当前单角色实机已通过；双角色两轮实机验证待进行。下文调研描述保留作为实施前基线，以文末进展为准。

分支：`dev/custom-model-design`，源码基线 `1f58b27f`。

范围：不同角色同时启用各自的模型 Mod；不要求同一角色的不同实例分别选择不同 Mod。世界角色、队友、角色展示界面仍可能是同一角色的不同模型实例和资源变体，需要分别匹配。

## 1. 建议结论

**正式替换提交点优先选择人物模型实例装配完成后。资源加载阶段负责识别原资源、读取 Mod 数据和准备可复用资源。**

这里的“装配完成”指目标实例的 Renderer、原 Mesh、材质、bones 和 rootBone 已由游戏建立，能够完成绑定校验。并非等待人物已经显示后再轮询替换，也不要求等待动画播放数帧。理想提交点是装配后、第一次绘制前；当前尚未证实所有角色路径都存在已覆盖的这一时点。

在“不同角色各用一套”的范围内，资源模板替换本身是可行的：同一角色的克隆继承同一套 Mod，符合需求。选择实例提交的主要依据是当前已跑通的后期替换能力，以及缓存命中、预加载、对象池复用、动态启停和模型变体覆盖的维护成本，不是同角色实例需要不同外观。

保留用户已确认的 **HG 原生渲染管线 LOD0 锁定 + NPC 距离与裁剪参数调整**。替换窗口的选择与 LOD 策略是两个问题，本建议不要求撤销当前 LOD 方案。

## 2. 技术基线与证据范围

- 工程是 Windows C++ 原生模块，通过 Host 的 IL2CPP 调用和 Hook 接入游戏；UI 为 .NET/WPF。不是可直接编辑的 Unity 游戏源码工程，不引入新的 Unity 包或 MonoBehaviour 框架。
- 既有调查记录的 UnityPlayer 版本为 `2021.3.34.0`，渲染管线为 HG 自定义管线。版本来自既有记录，本轮未重新读取游戏二进制。
- 用户确认整体模型替换链路已经跑通。本轮通过源码与既有实机记录研究多角色推广条件，未重新做游戏验收。
- 现有 BEM 测试包包含几何、蒙皮权重/索引和贴图，不包含独立骨架、bindpose、Avatar 或 AnimatorController。因此两条路径都应保留游戏原骨架与初始化过程。
- 不计算产物哈希。下文资源标识指游戏现有的资源键，不是要求重新计算文件摘要。

## 3. 当前实际入口与已有能力

| `DeliverySmsHook` | 已观察 NPC `CreateSMSInfoForPostModel` | NPC 另有装配路径；既有安洁样本未命中，覆盖仍待验证 |

### 3.1 早期资源交付的时序限制

现有记录确认安洁的 `FinishWithAsset → Instantiate → Base/Complex 后处理` 使用同一模板和克隆链路；41 个 Renderer 的 Mesh 指针/名称与 bones 长度在快照中一致。它没有证明逐槽骨骼引用、矩阵或动画内部状态全部一致，也不能推广到所有角色。

`DeliveryFinishHook` 源码明确资源回调可能发生在非主线程。Unity 对象创建、材质和 Renderer 修改不能简单塞进任意加载回调。即使转交主线程，也要证明游戏尚未克隆消费，否则“在资源加载时处理”并不等于“首次使用前已经替换”。

此外，该钩子当前先调用原 `_FinishWithAsset`。如果原函数内部通知消费者并触发克隆，原函数返回后的修改可能已经过晚。这是需要继续验证的时序问题，本轮不将其写成已证实的漏改。

### 3.2 网格正确性与替换窗口分开判断

既有调查记录指出早期和后期替换均曾出现同类蒙皮异常。当前 `BuildMeshFromComponent` 已包含从源 Mesh 初始化原生 `+0x1C8` 字段及上传后检查的代码。不能再用历史变形现象直接证明某个替换窗口必然错误；网格构建、绑定契约和生命周期分别验收。

## 4. 两条路径在多角色场景中的比较

| 场景/要求 | 资源模板交付时替换 | 实例装配完成后绑定 |
| --- | --- | --- |
| 不同角色同时启用不同 Mod | 可行，需要角色到资源的精确路由 | 可行，需要角色到实例的精确路由 |
| 首次显示即为 Mod | 有优势，但须证明修改先于克隆消费 | 需找到装配后、首绘前窗口；现有定时扫描可能闪现原版 |
| 角色资源早已预加载/缓存命中 | 不一定再次触发交付，需缓存模板和存量实例补偿 | 注册已有实例并在新实例就绪时处理 |
| 对象池复用 | 可能没有资源加载，旧模板/旧配置实例仍需维护 | 在复用/重新装配时核对实例代次和当前配置 |
| 运行中启用/停用单个角色 Mod | 改模板只影响后续克隆，存量实例仍需更新 | 可直接定位该角色的实例执行切换/还原 |
| 世界模型与 UI 展示模型 | 必须覆盖不同资源入口，分别验证布局 | 入口不同但可归一为实例绑定请求，仍需变体映射 |
| Mesh/贴图生成成本 | 模板可供多个克隆共享 | 也可缓存生成物；不必每个实例重建几何和贴图 |
| 原资源与回滚管理 | 同时维护模板、缓存、继承克隆的原始状态 | 维护实例原始绑定；生成资源统一计数释放 |
| 对原始初始化的影响 | 修改后的模板会被后续游戏装配过程消费 | 保留原模板与游戏装配流程，提交后仍需处理引擎回写 |

结论：资源模板路径能做好“启动前固定配置，随后所有克隆继承外观”。若它承担通用运行时管理，最终仍要增加存量实例、对象池和单角色回滚路径。实例提交可统一这些需求，并继续利用资源预备和缓存降低成本。

## 5. 多 Mod 的共同前置条件

无论选哪个窗口，以下现有单角色约束都需要改造。

### 5.1 按角色与资源变体识别部件

当前 `kActorMeshPrefix`、`BemPath()` 和早期部件表固定为管理员样本。`ApplyReplacement/PrepareReplacement` 的部件匹配主要使用原索引数；它只能作为已限定模型范围内的校验，不能作为跨角色的唯一身份。

建议先使用角色 ID、模型用途（world/UI 等）、资源变体及语义部件键定位目标，再检查原 Mesh 身份、顶点声明、bindpose 和骨骼槽位契约。识别不唯一时保留原绑定并记录原因，不能把第一个索引数相同的部件视为匹配。

实例使用受保护的对象引用、instance ID 和代次识别；Transform 路径和对象名称用于诊断与辅助匹配，不能单独承担实例身份。骨骼借调必须限定在同一实际角色实例，不能因为根路径字符串相同而跨实例借调。

### 5.2 将单包状态改为按角色管理

当前 `g_active_bem`、`g_replaced`、`g_installed_slots`、`g_mask_visible` 与 F11/F12 生命周期均围绕一套活动替换状态。早期路径也将 `g_early_bem` 写入同一个 `g_active_bem`。

建议保留现有 Host 调用、Mesh 构建与主线程 pump，增加三类明确的所有权：

- 角色选择：`CharacterId → ModId + Revision`，一个角色当前一套 Mod。
- 可复用资源：按 Mod 修订、模型变体、部件和源 Mesh/绑定兼容条件缓存 Mesh 与贴图。不同角色的 C9 不是同一个全局 C9。
- 实例绑定记录：保存角色、模型用途、实例代次及各 Renderer 原 Mesh、完整材质数组、bones/rootBone、显隐等状态。

缓存可以复用几何和贴图；Transform/bones 引用属于实例，不能跨角色共享。保留原资源引用，待所有用户解绑且越过实际销毁边界后再释放生成物。

### 5.3 材质必须隔离写入

当前常规 `InstallCustomTextures()` 从 `sharedMaterials` 收集 Material，并直接调用该 Material 的贴图 setter。保存材质数组不等于复制其中的 Material；如果其他角色或界面引用相同 Material，对它的修改可能传播。

建议为会修改的 Material 创建私有副本并挂到目标 Renderer，保存完整原数组。贴图和不变的 Mesh 可以共享；包含角色特定属性或由引擎动态改写的 Material 默认按实例隔离。早期路径已有私有材质创建逻辑可复用，但不能直接照搬其全局生命周期。

### 5.4 事务与 LOD 全局状态

以一个角色模型实例为提交单位：所有必需部件和材质准备及校验成功后，再集中写入；失败恢复已写入项。可选部件由映射显式声明，避免把样本的 11 个固定部件推广为所有角色要求。

当前常规应用允许部分部件成功后继续，早期路径虽先准备主要绑定，但纹理安装仍在提交后执行。两者都需要补齐正式的失败语义。

保留现行 LOD 策略，但它应由统一模块管理有效使用者：A、B 都启用时，关闭 A 不能调用全局解锁使 B 失去当前策略。最后一个使用者退出后才恢复原全局状态。现有全局设置保存范围不完整，详见 [LOD 现状文档](CUSTOM_MODEL_MULTI_LOD_BONE_ELEVATION_20260915.md#6-当前原生管线锁定实现)。多角色同时启用还应测量全局锁定下的实际开销。

## 6. 建议接入流程

```text
读取角色 → Mod 配置
  → 读取并校验各 Mod 文件（普通数据可后台准备）
  → 资源观察登记原模板/变体；Unity 资源准备交给主线程
  → 人物装配/模型切换/对象池复用通知
  → 归一为角色实例候选，合并 Base/Complex 等重复通知
  → 主线程校验身份、配置修订与绑定就绪条件
  → 获取或生成兼容的 Mesh/贴图，准备私有材质
  → 以实例为单位提交绑定并记录原状态
  → 引擎回写或再次装配时核对并修复该实例
  → 单角色停用/模型销毁时解绑，按使用者释放资源与 LOD 策略
```

最先调查 `ComplexModelViewPart.PostDealLoadedModel` 原函数返回后的窗口，结合 Base 路径核实嵌套关系，避免同一实例处理两次。NPC 与 UI 分别确认各自的入口，不能只挂一个方法就宣称全覆盖。

Hook 中尽量只登记候选，不执行重型文件读取、全场景扫描或资源销毁。默认由现有主线程 pump 处理；若测到 pump 已晚于首绘，再研究“预备资源已完成时，在确认安全的装配回调尾部做短小提交”，不先承诺零闪烁。

未就绪实例保留有限重试，实例销毁或配置代次变化即取消。启动时对已有实例进行一次登记；之后使用事件驱动，并保留共享的低频扫描补漏，避免每启用一个 Mod 就单独做一次全场景扫描。

## 7. 下一轮验证与决策条件

建议用管理员已知样本与另一名具有兼容 Mod 的角色做最小双角色验证。已有安洁资源观测有参考价值，但没有证据表明她的完整 Mod 样本已准备好。

| 检查 | 采样/验收条件 |
| --- | --- |
| 冷加载与预加载 | 分别记录资源交付、克隆、后处理、主线程提交；记录角色/变体、实例 ID、线程、帧号和配置修订 |
| 装配窗口 | 对比各阶段 Renderer 集合、原 Mesh、逐槽骨骼语义与引用、rootBone、bindpose、材质数组；明确哪些是稳定绑定条件 |
| 第一帧外观 | 结合画面或帧捕获检查是否闪现原版；不能用后处理日志替代首绘证据 |
| 双角色并存 | A 与 B 同屏、切主控、远近距离切换，网格/贴图/隐藏部件不串用 |
| 独立关闭 | 关闭 A 后 A 还原、B 保持 Mod；LOD 全局策略仍有效；最后关闭 B 才恢复全局状态 |
| 缓存与对象池 | 离队再加入、开关展示界面、切场景后，不依赖重新加载资源即可正确绑定 |
| 模型变体 | 世界/UI 分别匹配兼容布局，不因共享 Mesh 名或索引数误用另一变体 |
| 失败与恢复 | B 包不兼容或一个必需部件失败时，不改变 A，B 恢复完整原状态，资源仍有清楚的所有权 |
| 成本 | 统计构建次数、资源存量和主线程耗时；同一兼容资源不随每个实例重复构建 |

现有 `custom_model_lifecycle_tests.cpp` 覆盖单角色继承克隆、引擎回写、不同源资源、回滚失败保留等逻辑，可沿用测试边界。后续应补双角色相同 component ID/索引数不串用、单角色回滚不影响另一角色、共享材质隔离、LOD 最后使用者恢复等用例。本轮未新增或运行这些测试。

**决策门槛**：若装配入口能覆盖实际角色路径，且实例提交无可见原版闪现，采用实例提交作为默认正式路径。若特定路径存在首绘之前必须读取替换 Mesh 的已证实需求，再为该资源变体增加受控的早期模板策略；它仍共用上述角色路由、资源缓存和回滚管理，不另建一套互不相知的全局状态。

## 2026-09-15 双角色双路径验证实施

角色固定为已验证的管理员与佩丽卡，运行时新增 `target=both`；独立维护两份 BEM、renderer 记录、贴图安装记录、资产保留、刷新状态和回滚。上下文只在主线程操作保护内切换；共享原资源的卸载保护在最后一个角色释放时恢复。LOD0 全局锁检查任一角色是否活跃，单角色回滚不解除另一角色需要的锁。

两角色均使用 renderer 独立材质。保持管理员原组件联合匹配语义的风险需实机核对；本实验仍不代表任意 Mod 自动识别。F11 停用/回滚两个角色，F12 重建/重新启用两个角色。实验启动即 armed，便于捕获首次加载。

### 第一轮：实例路径（当前部署）

`%LOCALAPPDATA%\BetterEndfield\catalog\custom-model\runtime.ini`：

```ini
[CustomModel]
target=both
path=instance
```

Base/Complex PostDealLoadedModel 原函数完成后尝试替换，并保留活动实例扫描补偿。日志明确区分 `INSTANCE-BASE-END`、`INSTANCE-COMPLEX-END` 和 `INSTANCE-SCAN`。扫描成功不能证明首绘前替换，也不意味着 hook 覆盖了全部 NPC/UI 路径。

实机步骤：重启游戏；同队放入管理员和佩丽卡，依次观察两者与切换操控；分别进入角色展示后返回世界；按 F11 观察两者恢复，F12 观察两者重建。记录是否串材质、漏部件、AI/阴影异常以及刷新回写。实际视觉由用户确认，日志另行采样。

### 第二轮：资源路径（代码就绪，暂不启用）

第一轮确认后将 path 改为 `resource` 并重新启动游戏。在 `_FinishWithAsset` 原函数通知消费者之前、且确认 Unity 主线程时尝试修改匹配角色模板。模板材质使用 Array.Clone + Material 复制构造器，避免对 prefab 调用 renderer.materials。
