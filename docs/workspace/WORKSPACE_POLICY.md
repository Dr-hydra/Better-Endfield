# 工作区迁移与资料管理规范

本文是新工作区当前采用的管理规范。统一配置读取、资源工具链、构建路径、文档和测试入口已经接入；本次未构建、实机验证或部署。

## 工作区与配置

- 新工作区为 `F:\Better Endfield`，整理分支为 `chore/workspace-reorganization`。`F:\Better Endfield_legacy` 是完整回退资料，不把它当作可清理缓存。
- `F:\zmd` 不参与本次整理。BEM 转换已经结束，仅保留经验与后续指定包修复资料。
- 可变路径、工具选择、采集参数、输入选择和版本兼容资料走配置；格式定义、ABI 和边界约束仍由代码保证。
- 使用仓库默认配置、本机覆盖配置和显式命令行参数。默认配置可跟踪，本机配置、私有参数和凭据不进入 Git。路径优先相对工作区根目录。
- 软件运行时用户设置、开发工作区配置、游戏版本兼容资料分别管理，不强行塞进一个配置文件。

本机配置示意如下，字段仍待落实到统一读取器：

```json
{
  "paths": {
    "inputs": "inputs",
    "research": "research",
    "temp": "temp",
    "build": "build",
    "releases": "releases",
    "toolchains": "toolchains"
  },
  "test": {
    "be_install_dir": "E:\\Better Endfield"
  }
}
```

本机 BE 安装目录是实际部署和测试目标。源代码目录、构建目录和安装目录不能混用；生成资源、编译与部署是独立步骤。

## 分类与版本

- 现行说明按模块组织：`docs/<module>/`，提供统一索引。模块邻接 README 和资源来源记录保持可定位关系。
- 版本相关研究按 `research/<module>/<game-version>/<platform>/<topic>/` 组织；日期保留在元数据，不作为主要分类方式。
- 共用输入按 `inputs/<game-version>/<platform>/<snapshot>/` 保存，多个模块通过输入 ID 引用，不各自复制一份。
- 游戏版本、资源快照、工具版本、BEM 格式版本和软件版本是不同维度。记录来源清单与代码提交；未知版本标记未知，不凭日期猜测。
- 每个专题保留入口、脚本、输入指针、结论、验证范围和未解决事项。结论区分现行、待验证、已取代；通用说明不按每个游戏版本复制。
- 文档保持明确的维护来源，英文版、skill 参考文档与随包副本说明同步关系。移动固定消费文档时同步修改打包、程序读取和证据引用。

## 资源更新工具链

- 统一接入配置的范围包括输入刷新、角色扫描、动作预设、语音、战斗数据、头像及双端资源布局，不只修改入口脚本。
- 原始快照和必要解析输入保存到持久输入区；可再生的处理中间文件放 temp/build；随发布资源保存到明确的持久资源位置。
- 共同资源保留一份维护来源，平台差异独立记录。PC/Android 打包所需副本在生成分发布局时产生。
- 人工修正规则、增量来源和自动生成结果分开保存。当前基线之外的人工增量不得被全量生成覆盖。
- 提取优先利用 VFS 已有内容标识。生成任务记录输入快照、工具版本和参数，无变化时复用已有完整结果，不重复写入或自动创建时间戳备份。
- 相同内容复用实体，来源和版本记录分别保留。必要的新内容指纹在写入过程中计算，避免迁移时默认对全部历史大型文件重算；不能仅按文件名和大小认定内容相同。

## 可清理目录

- `temp` 和 `build` 明确允许清空，只保存可重建内容。包括临时解包、编译中间文件、普通构建日志和临时输出。
- 人工脚本、映射、配置、原始采样、重要诊断、研究结论、唯一素材和编辑工程不得只保存在 temp/build。
- 正式发布包存 releases，工具环境存 toolchains；它们不因“由工具生成或下载”就自动成为缓存。
- 子进程、Python 临时文件、CMake/.NET/Gradle 中间输出也使用配置路径，不继续散落在源码、research 或系统临时目录。
- 清理只操作配置指定的允许清理目录。验证实际路径，拒绝与输入、研究、工具链、安装目录、源码和 legacy 回退目录重叠的目标，不按目录名称全盘搜索删除。

## 测试脚本管理

### 类型与归属

| 类型 | 归属和规则 |
| --- | --- |
| 长期回归测试 | 跟随源码维护，按模块和行为分类，覆盖仍受支持的功能与格式；通用测试不强行绑定游戏版本 |
| 版本相关验证 | 指明游戏版本、平台、资源快照、输入和预期；对应研究专题或版本测试套件 |
| 临时诊断与实验 | 只要包含人工逻辑或可能有后续价值，就放持久研究专题；temp 只放可重建的临时输出，不把“临时脚本”理解为可以丢失的源代码 |

现有 `native/tests`、创作者工具测试和平台测试先保持构建关系。目录整理时同步更新 CMake、导入路径和测试发现规则，不为统一外观直接搬动全部源码。

### 清单与执行

- 统一登记测试套件或脚本入口，不人工重复登记每个断言。复用原有测试发现机制；登记稳定 ID、模块、用途、负责人、适用平台/版本、依赖、输入和执行方法。
- 提供可按模块、平台、版本和测试类型筛选的执行入口。真实游戏测试单独显式执行，使用配置中的本机 BE 安装目录。
- 记录实际源码提交、工具/测试二进制版本、输入快照与执行命令。已有旧 EXE 不能默认代表本次源码的测试结果；排除出默认构建的测试目标要单独确认版本。
- 区分通过、失败、跳过、依赖缺失和未执行。静态核对、离线包验证、模拟验证与实机验证分别记录，不能互相替代。
- 普通测试临时结果写 build/temp；有价值的失败诊断、采样和结论直接归入持久研究专题，保留版本与输入来源。
- 新测试以实际行为、边界或回归问题为依据，避免仅复述实现。验证范围与改动相关，已通过的同一检查不反复重跑，除非有新改动、失败或未解决疑点。

### 过时与冗余处理

- 模块行为改变、游戏输入更新、功能移除或加入新测试套件时，顺带审查相关旧脚本。
- 重复判断依据是覆盖行为、输入域和预期是否相同；合并重复入口时保留不同边界用例。旧版本仍在支持范围内的兼容回归不能仅因日期旧而删除。
- 已替代脚本记录替代套件 ID；失效测试记录失效原因和适用范围，更新预期或退役，不把失败直接屏蔽成通过。
- 删除或归档前确认没有构建、测试入口、修复脚本或其他专题读取它，且独有用例、人工逻辑和证据已有合适归属。
- 不维护两个并行的“正式测试”集合。一次性验证被正式回归覆盖后，及时收口旧入口；历史结论保留必要追溯，不让过程记录冒充现行测试说明。

## 迁移顺序与边界

1. 确定目录与配置字段，建立统一路径读取和测试套件清单。
2. 改造资源更新链、构建和临时输出位置，再迁移必要输入与工具。
3. 建立模块文档及研究索引，迁移资料时同步引用与版本来源。
4. 整理测试入口、输入和状态，处理有明确替代关系的重复或过时内容。
5. 分批提交与核对引用，保留旧目录回退。本次实施只做静态与离线模拟核对，不执行真实资源刷新、构建、实机测试或覆盖安装目录。
