# 1.6.3 官方启动入口局部调查

日期：2026-10-15。对象为本机 `D:\Hypergryph Launcher\Launcher.exe` 和 `D:\Hypergryph Launcher\1.6.0\Games.exe`。本次只读取快捷方式、注册协议、文件及少数相关函数的机器码，未启动启动器或游戏，未发送窗口消息，未修改官方配置，没有建立全量反编译数据库。

## 当前结论

已经确认官方快捷方式入口、命令行解析和部分实例间通信，但**尚未找到可确认“不点击 UI 就直接开始游戏”的官方参数或 IPC 命令**。`--game=endfield --reason=4` 的来源可靠；它携带游戏选择和启动来源，不能仅据此断言会自动开始游戏。

目前经实机验证的正常路径仍是：在官方启动器中点击开始游戏，由 `Games.exe` 创建 `Endfield.exe`，游戏随后通过既有 XInput 代理加载 BE。本次静态结果不改变这个验证边界。

## 已确认的官方入口

本机桌面“明日方舟：终末地.lnk”内容：

```text
目标：D:\Hypergryph Launcher\Launcher.exe
参数：--game=endfield --reason=4
工作目录：D:\Hypergryph Launcher
```

本机 `hypergryphlauncher-*` 注册协议的打开命令为：

```text
"D:\Hypergryph Launcher\Launcher.exe" "%1"
```

本机快捷方式直接使用上层 `Launcher.exe`，没有直接指向带版本目录的 `Games.exe`。集成官方路径时，这可以避免将 `1.6.0` 目录固定到生产代码中。

## 局部机器码旁证

下列地址均为本机文件的静态 VA，ImageBase 为 `0x140000000`，仅用于复查本次证据，不作为跨版本挂钩地址。

| 对象 / 地址 | 已观察到的行为 | 可以支持的结论 |
| --- | --- | --- |
| `Games.exe`，`CCmdLineConfig::_Init`，`0x1402e0890` | 调用 `GetCommandLineW`、`CommandLineToArgvW`，注册 `--reason`、`--game`、`--oldVer` | `--game` 和 `--reason` 是实际解析的参数，不只是未使用的字符串 |
| `Games.exe`，`0x1402e0580` | `--reason` 回调调用 `QString::toInt(..., 10)`；接受 0–7，其他值归零；写入配置对象 `+0x18` | reason 是有限的来源枚举；不能通过任意填写数值推导出自动开始行为 |
| `Games.exe`，`0x1402e0110` | `--game` 回调复制字符串到配置对象 `+0x20` | 支持选择指定游戏；没有在该回调中直接启动游戏 |
| `Games.exe`，`0x1401bda90` | 读取复选框状态，将静态文本 `--reason==3` 交给设置辅助函数；附近 UI 文本为 `Auto startup` | 该分支属于启动器自启动设置，不应将 reason 3 当作“自动开始游戏”参数；保留文件中的原始双等号，不自行修正或使用 |
| `Launcher.exe`，`0x140018c30` | 协议处理分支引用 `hypergryphlauncher`、`gryphlinklauncher` 和 `open`，组装 `--game=` 与 ` --reason=6` | 官方协议最终转为游戏选择参数和来源 6；完整 URI 格式及动作语义未继续追踪，不提供猜测示例 |
| `Launcher.exe`，`CHgAssist::Startup`，`0x14001c9e0` | 引用 `Games.exe`；`0x14001cc68` 调用 `ShellExecuteW`，操作为 `runas` | 上层入口负责启动带版本目录的官方程序并请求正常 UAC 提权；直接绕开上层入口的行为没有在本次验证 |

`CCmdLineConfig::_Init` 还注册了若干非可读名称的内部选项。本次没有将其猜测为受支持的启动开关，也没有枚举或执行这些选项。

## 实例间通信

`Games.exe` 的 `0x14018a540` 读取已解析的游戏选择，组装 `--game=%1`，并在 `0x14018a72f` 调用 `SendMessageTimeoutW` 发送 `WM_COPYDATA`。这证明它具有向既有窗口传递游戏选择的通路。

本次没有继续追踪接收处理器，因此只能确认发送内容，不能断言该消息能直接启动游戏。没有发送任何实际窗口消息，也没有做 UI 自动点击。

另可见 `CPatchController::CreateIPC`（`0x140292700`）及共享内存相关字符串；这些明确涉及更新控制器。不能把更新器的 IPC 当成游戏启动接口。可见 `QSharedMemory` 导入本身也不足以证明存在可对外调用的“开始游戏”服务。

## 配置与轻量运行边界

检查了 `1.6.0\eld_Games.db` 与 `Cache\Config\Config` 的格式。它们不是可直接以只读 SQLite 打开的普通数据库；本次没有进一步解密或改写，也没有读取账号认证数据。

未找到已确认的无窗口、仅启动游戏后退出或轻量常驻模式。官方启动器的开机自启动、静默更新，与“不显示 UI 直接启动游戏”是不同的行为，本次证据不能相互替代。

若采用完整官方入口，Steam 对新建进程、既有启动器实例、UAC 提权和启动器常驻的跟踪效果仍需一次实际启动验证。时长、运行状态和覆盖层尚不能保证。此记录也不验证其他研究中的父进程启动桥或校验模拟方案。

## 建议使用方式

1. 需要已经证实可工作的路径时，继续使用官方启动器开始游戏并加载 XInput。
2. 需要由 BE 或 Steam 打开官方启动器时，可复用现有 `.lnk` 的入口和参数，但界面不要承诺“直接开始游戏”。
3. 若后续仍要实现免点击的官方路径，应定向补查 `WM_COPYDATA` 接收处理或实际快捷方式行为；不需要为此对整个启动器或游戏建立全量数据库。
